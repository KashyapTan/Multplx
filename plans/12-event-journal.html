Plan 12 · Multplx

mx-journal — One Timeline per Task

An append-only, observability-only JSONL journal per task: every existing state writer also emits one structured event, so "what happened to task X and why" becomes mx-timeline <id> instead of hand-correlating five state files. The scattered per-purpose state files stay the operational truth; the journal is a projection, never an input.

Phase 9 (post-port) Effort: Medium Risk: Low Post-port improvement (maintainer request, 2026-07-27)

Overview

Multplx's on-disk state is deliberately scattered by purpose. state/<id>.status is an append-only event log of wake-worthy transitions (the header of firstmate/bin/fm-crew-state.sh is explicit: it is "an append-only, best-effort EVENT LOG", never the current state). Gate run records live under state/<id>.gate/ (run.json plus findings/, per plan 10). Workflow run records live under state/<run-id>.workflow/ (plan 11). Decision holds are structured backlog entities managed by mx-decision-hold.sh. The wake queue is state/.wake-queue. Delivery attestations land in state/<id>.delivered (plan 09).

That scattering is a design virtue this plan preserves: each file has one owner, one purpose, and is independently reconstructable, which is exactly what makes the reconciliation oracle and the crash-recovery story deterministic. The cost is purely observational — reconstructing the full story of one task ("why did the gate run twice? when did the hold open? which signal tier decided it was blocked?") means opening several files and mentally merging timestamps.

This plan adds the missing read-side convenience without touching the write-side architecture: every existing writer additionally appends one structured JSONL event to a per-task journal, via a tiny shared helper (mx_journal_emit). A new reader, mx-timeline, renders that journal as a single chronological, source-attributed story. Nothing in the system ever reads the journal for control flow.

A specific payoff worth naming: plan 05's classifier precedence rule (native event > schema-validated self-report > regex heuristic) is deterministic but currently invisible after the fact — you can see the verdict, not the contest. The journal's status.classified event records which tier won and what the conflicting lower-tier signals were, making precedence auditable per decision.

Critical invariant — observability only

The journal is never read for control flow. It is not an input to reconciliation (mx-actor-state.sh), not an input to the classifier (mx-classify-lib.sh), not consulted by the watcher, the workflow engine, or the gate. The scattered per-purpose state files remain the operational truth; the journal is a lossy-tolerant projection of them. This is the same "event log is not truth" invariant the port protects (porting.md §2.3) — the journal must not become a second, more tempting truth. A grep-based tripwire test enforces this permanently (see Test plan).

Critical invariant — best-effort writes

A journal write failure must never fail the operation being journaled. mx_journal_emit appends best-effort: on any error (unwritable dir, full disk, malformed detail JSON) it warns once per process on stderr and returns 0. A task must spawn, report, gate, and deliver identically whether or not its journal is writable.

Goals & Non-goals

GoalsNon-goals
  • One append-only JSONL journal per task: state/<id>.journal.
  • One shared emit helper, bin/mx-journal-lib.sh (mx_journal_emit) — writers append inline, no daemon.
  • One closed, documented event-type vocabulary, owned in one place (docs/journal-events.md).
  • Instrument every existing writer: spawn, validated status reports, classification verdicts (with the winning precedence tier and the losing signals), gate steps, decision holds, workflow stage transitions, delivery.
  • A human-readable reader: bin/mx-timeline.sh <id> with --since / --event filters and optional --html via the vplan module.
  • Purely additive — zero existing tests change.
  • No consolidation of state. The per-purpose files (.status, .gate/, .workflow/, holds, wake queue) keep their owners and formats untouched.
  • No control-flow reads. No script may branch on journal contents — ever.
  • No journal daemon, no watcher integration, no wake events triggered by journal writes.
  • No global (cross-task) journal in v1 — mx-timeline reads one task; a fleet-wide merge is a possible later reader-side feature.
  • No retention/rotation machinery in v1 — journals are small text files torn down with the rest of state/<id>.*.
  • No backfill of pre-journal tasks.

Target design in Multplx

Journal file and event shape

One JSONL file per task, sibling to the other per-task state files: state/<id>.journal. (A state/journal/<id>.jsonl subdir was considered and rejected: the flat state/<id>.* sibling convention is what mx-teardown.sh and the herdr projection logic already sweep, so a sibling file gets lifecycle handling for free.) Every line is one event:

{"ts":"2026-07-27T18:42:07Z","task":"fix-auth-42","source":"mx-report","event":"status.reported",
 "detail":{"raw":"blocked: CI needs GH_TOKEN scope","state":"blocked","validated":true}}
  • ts — UTC ISO-8601, second precision. Ordering within a file is append order; ts is informative, not a sort key.
  • task — the task id (same id as the state/<id>.* family).
  • source — the emitting script's basename (mx-spawn, mx-report, mx-watch, mx-deep-review, mx-workflow, mx-decision-hold, mx-deliver).
  • event — one of the closed vocabulary below. Unknown event names are rejected by the lib at emit time.
  • detail — event-specific object; each event type's required keys are documented with it.

The emit helper — bin/mx-journal-lib.sh

# mx_journal_emit <task-id> <event> <detail-json>
#   - validates: task-id is a safe slug; event is in the closed vocabulary;
#     detail-json parses (jq -e . or, when jq is absent, a conservative shape check)
#   - composes the envelope (ts, task, source from MX_JOURNAL_SOURCE or $0 basename)
#   - single atomic O_APPEND write of one line to $STATE/<task-id>.journal
#   - BEST EFFORT: on any write error, warn once per process to stderr, return 0
#   - a MALFORMED CALL (bad event name, unparseable detail) returns non-zero so
#     tests catch writer bugs — but callers invoke it with `|| true` semantics
#     baked in via mx_journal_try (the wrapper production code actually calls)

Two entry points on purpose: mx_journal_emit (strict, returns non-zero on caller error — what tests exercise) and mx_journal_try (the production wrapper: strict-validate, then swallow every failure). Writers append inline; there is no journal daemon, no queue, no lock — single-line O_APPEND writes under PIPE_BUF are atomic on POSIX filesystems, and interleaving across writers is acceptable because order-of-record is append order per event, not a transactional claim.

The reader — bin/mx-timeline.sh

mx-timeline <id>                    # chronological, source-attributed, human-readable
mx-timeline <id> --since 2h         # only events newer than a duration or ISO timestamp
mx-timeline <id> --event gate.*     # filter by event glob
mx-timeline <id> --json             # raw JSONL passthrough (filtered)
mx-timeline <id> --html             # shareable artifact via the vplan module (plan 08)
18:42:01  mx-spawn        task.spawned          kind=actor backend=tmux branch=fix/auth-42
18:49:33  mx-report       status.reported       blocked: CI needs GH_TOKEN scope  [validated]
18:49:34  mx-watch        status.classified     blocked  (tier: validated-report; regex heuristic disagreed: "working")
18:52:10  mx-decision-hold hold.opened          fix-auth-42-decision-gh-token-scope
19:04:41  mx-decision-hold hold.resolved        → routed to fix-auth-42
19:31:02  mx-deep-review  gate.step.finished    step=review round=1 findings=2
20:12:55  mx-deliver      delivery.pr_opened    https://github.com/…/pull/108

Malformed lines (torn writes, hand edits) are skipped with a one-line warning and a count — the reader is as tolerant as the writer is best-effort. --html calls mx-vplan-lib.sh to render the same rows as a self-contained artifact; it is optional and degrades to an error message if plan 08's module is absent.

Implementation steps

  1. Lib + vocabulary first. Create bin/mx-journal-lib.sh new with mx_journal_emit / mx_journal_try and the event-name allowlist, and docs/journal-events.md new documenting every event type and its required detail keys. Land with the lib's own tests before any writer is touched.
  2. Instrument mx-spawn.sh mod — emit task.spawned right after state/<id>.meta is written (the journal line must never precede the metadata it describes).
  3. Instrument mx-report.sh mod — emit status.reported alongside the durable state/<id>.status append (plan 03). The MCP path (mx-report-mcp.mjs) needs no change — it already shells through mx-report.sh.
  4. Instrument the classify seam — mx-watch.sh mod and mx-supervise-daemon.sh mod emit status.classified at the point where plan 05's precedence rule picks a winner, recording tier and conflicts. mx-classify-lib.sh itself stays a pure function library — the callers journal, not the lib.
  5. Instrument the deep-review orchestrator — mx-deep-review.sh mod emits gate.step.started/gate.step.finished where it updates state/<id>.gate/run.json.
  6. Instrument the workflow engine — mx-workflow.sh mod emits workflow.stage.entered/workflow.stage.gated where it updates state/<run-id>.workflow/. Workflow events journal under the run id.
  7. Instrument decision holds — mx-decision-hold.sh mod emits hold.opened in hold and hold.resolved in resolve (after the final Done step, so the journal never claims a resolution that did not durably complete).
  8. Instrument delivery — mx-deliver.sh mod emits delivery.queued/delivery.pushed/delivery.pr_opened alongside plan 09's attestations.
  9. Build the reader. bin/mx-timeline.sh new: render, --since, --event, --json, --html (vplan). Golden-file test fixture in the same commit.
  10. Docs + registration. AGENTS.md gets a one-line pointer ("timeline of a task: mx-timeline <id>") mod; register tests/mx-journal.test.sh and tests/mx-timeline.test.sh in mx-test-run.sh's family map mod in the same commits as the tests.

(c) New tests

TestAsserts
tests/mx-journal.test.sh(1) Events append in order with valid shape — emit three events, assert three JSONL lines, each with ts/task/source/event/detail and monotone append order. (2) Malformed emit calls are rejected by the strict lib entry point: unknown event name, unparseable detail JSON, unsafe task id — all return non-zero and write nothing. (3) Write failure never fails the wrapped operation: with a read-only state/ fixture (chmod-based, same pattern as upstream permission fixtures), mx_journal_try returns 0 and warns once; then an end-to-end check that mx-report against the read-only journal still durably appends to .status and exits 0. (4) Vocabulary sync: every event name in the lib allowlist appears in docs/journal-events.md and vice versa. (5) The tripwire: grep bin/ for any read of *.journal (grep -rn '\.journal' bin/ filtered to non-append usage) and assert the only hits are mx-journal-lib.sh (append) and mx-timeline.sh (the sanctioned reader) — mirroring the static-contract style of fm-instruction-owners.test.sh, so "observability only" is enforced forever, not just reviewed once.

Risks & open questions

Risk — the journal becomes tempting truth

The whole point of a complete timeline is that it looks authoritative. Future changes will be tempted to read it ("the journal already knows the last gate outcome…"). Mitigation is structural, not advisory: the grep tripwire in mx-journal.test.sh fails CI the moment any production script reads a journal, and docs/journal-events.md opens with the invariant in bold.

Risk — emit placement on control paths

An emit placed inside a set -e region without the mx_journal_try wrapper could turn a journal failure into an operation failure. Rule: production code only ever calls mx_journal_try; the strict entry point exists for tests. The read-only-dir end-to-end test catches the most likely regression (mx-report).

Open question — concurrent-writer interleaving guarantees

v1 relies on POSIX O_APPEND atomicity for single lines under PIPE_BUF. If a detail payload ever exceeds that (very long findings summaries), lines could tear. Options if it bites: truncate detail values in the lib (cap enforced at emit), or take the wake-queue-style lock for oversized writes. Deferred until observed; the reader already tolerates torn lines.

Open question — retention

Journals die with task teardown alongside the other state/<id>.* files. Should completed tasks' journals be archived (e.g. into data/) for post-mortems? Deferred — teardown already preserves what plan 09/10 attest durably; revisit if a real post-teardown investigation wants one.
