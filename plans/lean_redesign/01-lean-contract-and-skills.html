Lean Contract and Operational Skills

Replace the mandatory engineering playbooks with a short operating contract, concise task instructions and practical CLI references.

Phase 01 of 12Effort: MediumRisk: MediumRevised · 2026-09-14
Implementation guide

Read porting.md for the shared product contract, skill disposition, migration boundaries and release acceptance. This phase is planned, not implemented.

Dependencies: Baseline repository review.

Overview

The old root contract prescribes who may code, how bugs must be investigated, when workers stop, how findings are answered and how every response is phrased. Removing skill files alone would leave those rules in generated briefs and other instruction surfaces. This phase removes the policy at its actual prompt sources.

Implementation steps

  1. Inventory all injected instructions.Read root files, skill bodies, generated delivery/scout/daemon templates, Cursor rules, session protocol text and optional headless prompts. Classify each requirement as coordination mechanics, repository fact or removable engineering policy.
  2. Rewrite the dormant contract.Use the small-contract outline in porting.md. Retain the main no-coding boundary and free nested delegation, state human-only PR merging, retain selected workflow obligations and make review tools opt-in. Keep AGENTS_E.md dormant during development.
  3. Apply the skill disposition.Remove the prescriptive internal skills and universal override procedure identified in the guide; consolidate recovery and persistence mechanics. Do not relocate their removed methods into another automatically loaded file.
  4. Reduce the generated brief.Keep assignment, success criteria, working location, task/report binding and meaningful constraints. Remove the two-obstacles stopping rule, read-only GitHub rule, forced project-memory edits and blanket ban on lifecycle commands. Subsequent phases implement the matching runtime freedoms.
  5. Repair references and discovery.Update retained skill triggers, symlink targets if needed, documentation inventory, owner pointers and contract tests. Link current development references to the dormant root file without teaching startup to load it.
  6. Record the reduction.Compare line/byte counts for the root and representative brief variants. Inspect the emitted prompt text for removed rules, including text embedded in Rust strings, without building a new instruction-budget service.
  7. Keep reliability out of engineering playbooks.Link concise operational guidance to CLI-owned acknowledgement, identity, summary and evidence commands as they are implemented. Briefs retain scope, accepted revision, acceptance criteria and original artifact pointers. Do not inject all task transcripts or expand the root contract into a scheduler procedure.
  8. Keep one multi-repository conversation discoverable.Point the short contract and retained project CLI guidance to A9. Generated briefs carry project/checkout identity and scoped repository instructions; remove URL-and-clone requirements and project-mode interviews from ordinary local intake.
  9. Describe launch-anywhere and built-in worktrees.Treat multi-repo delegation as ordinary orchestration, make discovery roots optional and replace Treehouse setup references with concise built-in CLI guidance. Keep allocation mechanics out of general coding policy.
  10. Document the coordinator assignment.Add concise A11 scope/parent-channel guidance and the sub-orchestrator CLI reference. Both coordinator roles delegate project coding; retain free delegation and avoid importing Secondmate engineering procedures.

Orchestrator and assignment contract

The main agent may inspect and research, discuss direction with the human, write plans and briefs, dispatch work and maintain coordination state. It delegates project source and test-code changes even for small fixes. Researcher, implementer and reviewer prompts describe outcomes and evidence, without becoming prescriptive engineering skills.

  • No root AGENTS.md is recreated in the development checkout.
  • Fresh instructions discover A1-A11 through the guide, preserve the main no-coding boundary and describe the actual implemented CLI rather than optional recommendations.
  • Fresh instructions describe one shared chat, nested dev-root discovery and local reuse without turning project selection into a new role or approval gate.
  • Fresh prompts never require a dev-folder cwd or an external Treehouse installation.
  • The assigned A11 foundation and focused interface checks pass; Phase 05 owns end-to-end coordinator integration, avoiding a circular dependency.
