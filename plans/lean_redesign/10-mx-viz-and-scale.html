MX Viz and Concurrent Task Visibility

Make twenty tasks, their sub-agents, decisions and delivery evidence legible from one shared state model.

Phase 10 of 12Effort: HighRisk: MediumComplete · dashboard and scale verified · 2026-09-17
Implementation guide

porting.md owns the revised product direction. The architecture assessment explains the scale risks. This page defines the target behavior; the implementation evidence records the verified result and its boundaries.

Dependencies: 02, 04, 08, 09. Visual design and fixtures can begin earlier against the Phase 02 typed snapshot contract.

Overview

MX Viz must make 10-20 simultaneous tasks understandable through one orchestrator. A label substitution on the current flat worker tree is insufficient. The display needs to separate user tasks, execution attempts, sub-agent roles, workflow stages and questions awaiting the human.

Behavior boundaries

PORTFOLIOTwenty tasks grouped by project, outcome and priority.
ASSIGNMENTSResearcher, implementer, reviewer and their current attempts.
HUMAN ATTENTIONConcrete decisions and PRs ready for human review or merge.
FRESHNESSUnknown, stale, interrupted and partially observable states stay explicit.

Implementation steps

  1. Define the shared projection first.Expose task identity, project, accepted plan revision, task state, current workflow stage, dependencies, owner, child sessions, role, attempt generation, latest meaningful event and observed-at/freshness. These field semantics are required by A2/A4/A7; publish the implemented schema before connecting readers. Chat summaries and MX Viz consume the same read model.
  2. Make tasks the overview unit.Show a compact project/task list with search and status/role/project filters; expand a task into its agent tree and stage detail. Count 20 tasks separately from 40 sessions or retries. Preserve stable task identity, focus, expanded rows and selection while polling.
  3. Show the human collaboration loop.Link original research, accepted plan revision, implementation brief, relevant review/test evidence and PR. Show a decision's question, current target and waiting time. Keep task-specific human choices out of unrelated task summaries. Requested vplan reviews link to their existing tool surface; the dashboard does not start one automatically.
  4. Represent delivery and quality honestly.Separate agent done, checks passing for the current revision, review requested/completed, PR open, human merge pending and merged. Absence of deep-review is not an error. Missing provider evidence is unknown, not idle or completed. Explain which tasks a failed dependency blocks.
  5. Bound observation cost.Measure the current serial per-task subprocess collection and the service mutex held during refresh. Design a bounded canonical collection path with per-provider deadlines and cached observations. Serve the last good snapshot with explicit staleness while one refresh is in flight; the UI must not make watcher progress depend on an HTTP request.
  6. Coalesce updates.Prevent overlapping client polls, back off hidden tabs and compare meaningful content revisions while exposing freshness separately. Preserve concurrent-request coalescing. Do not add SSE, WebSockets or another daemon unless measurements justify them.
  7. Preserve the read-only boundary.Keep GET-only observation, loopback binding, path containment, scriptless artifact rendering and identity-bound shutdown. No new approve, merge, spawn or task-state-edit endpoint is part of this plan.
  8. Build a readable visual hierarchy.Use a compact task overview and expandable detail with consistent spacing, typography, status labels and priority. Add useful empty, loading, partial-error and stale states; expose decisions and ready PRs prominently without hiding dependencies or evidence.
  9. Connect one canonical collection path.Implement bounded snapshot collection and partial results from A4 using Phase 02 schema. Serve the last good cache without holding the runtime mutex over external calls; reuse Phase 04 watcher observations where valid. Age and freshness update even when content is unchanged.
  10. Verify interaction and performance together.Exercise keyboard navigation, narrow/wide layouts, multiple tabs, hidden-tab backoff and stable focus/filters/expanded rows while task states change. Measure A8 targets with a documented machine and workload; retain failures as open acceptance.
  11. Expose project identity for workspace clients.Use Phase 02 project/checkout records in the canonical snapshot and dashboard filters. Show all running repos together, disambiguate same-named paths and retain stable task deep links. Phase 11 TUI consumes this projection; selecting a dashboard project is a view filter, never task reassignment.
  12. Expose actual allocation state.Read the internal manager projection for worktree path, allocation owner/generation, retained/leased state and recovery issues. Distinguish a stopped agent from disposable work and remove any dependency on parsing Treehouse status.
  13. Show domains and reliable parent communication.Add A11 domain overview and expandable coordinator/task lineage to the shared projection. Show current owner, pending human decisions, stalled handling, undelivered outcomes and partial homes; distinguish task counts from coordinator sessions.

Test plan

  • Fixtures with 0, 1, 5, 10 and 20 tasks; nested researcher/implementer/reviewer assignments; persistent sessions; duplicate attempts; mixed projects; open decisions; optional tools; current and stale PR checks.
  • Unknown child home, slow backend, one failing snapshot source, cancelled/replaced implementer, out-of-order completion and selected-plan revision change.
  • Existing tests/mx-viz.test.sh, Rust services-runtime tests and snapshot reconciliation suites retain read-only, loopback, caching, identity and artifact security guarantees.
  • Browser checks for narrow and wide viewports, keyboard use, expanded-row stability and distinction between tasks and sessions. Role labels are text, not only color.
  • Meet the accepted A8 performance targets on a recorded reference machine, including cached API latency, healthy 20-task refresh and initial interactivity. Record measurement method and samples; a failed or unavailable result remains open acceptance, not a reason to lower the target.
  • Open multiple dashboard tabs while workers report and one backend stalls. Record cache hits, refresh count, CPU, snapshot latency, oldest queued-event age and time to show fresh events. No extra worker or watcher load proportional to tab count should be required.
  • Inspect screenshots or browser output for 0/1/5/10/20 tasks on narrow and wide layouts, including long task names, nested assignments, decisions, stale observations and failed dependencies.
  • Compare backend probe counts for one and multiple tabs, stall one provider and verify usable cached views plus continued healthy reporting. Record accepted target results and measurement conditions.
  • Render three differently nested repositories with concurrent tasks and duplicate display names; switch filters and verify correct paths, evidence and unchanged task bindings across TUI/CLI/Viz projections.
  • The dashboard accurately shows retained open-PR work, persistent zero-process leases and uncertain legacy allocations with Treehouse absent.
  • At 20 tasks across several domains, both root and expanded views retain focus and truthful counts while a coordinator is unavailable and multiple viewers share cached observations.

  • The assigned A11 integration and its focused check above pass with Phase 05.
Integration risk

The current display treats task-shaped worker records as its main tree. Do not relabel them as distinct agent sessions without the Phase 02 model, or flatten persistence and retries into misleading active-task counts.
