Workspace Entry and Project Discovery

Launch from anywhere, reuse local repositories and enter the same orchestrator conversation.

Phase 11 of 12Effort: HighRisk: HighComplete · scoped acceptance · 2026-09-18
Implementation guide

A9 in porting.md owns the accepted workspace contract. This phase implements that contract; it does not create a per-repository orchestrator or replace the existing harness conversation.

Dependencies: 02, 04, 09, 10. Project identity is implemented in Phase 02. Discovery, packaging and TUI design can begin against those contracts earlier; final integration requires migration, durable request routing and the shared projection.

Overview

The global launcher currently activates a shell or a named harness, validates a repository-based runtime and deliberately ignores the caller's project. The registry resolves delivery settings for flat managed clones, and a live home owner causes launch refusal. Extend these boundaries into a global workspace entry: configurable nested discovery, reuse of existing paths, durable multi-repository task intake, reconnection and a small terminal home screen.

Implementation steps

  1. Separate the three path identities.Keep installed runtime, operational home and discovery roots independent. Capture the caller's directory before harness startup changes context. Any caller directory is valid without Git metadata, and selecting a project never selects a new operational home.
  2. Implement configurable discovery.Persist roots, traversal/depth settings, exclusions and symlink policy through the configuration owner. Allow optional roots without blocking chat entry; never automatically scan an arbitrary launch directory. Discover configured roots incrementally, cache results and expose refresh/progress. Recognize linked worktrees and nested repository boundaries; bound traversal and avoid executing discovered project content.
  3. Reuse local projects.Register selected checkouts idempotently through Phase 02 identity, resolve exact aliases/paths and present candidate paths for ambiguity. Handle overlapping roots, moved paths and separate clones without conflation. Unversioned folders retain their real capability limits and never silently become GitHub repositories.
  4. Expose durable intake commands.Implement the A9 command experience and exact help with a noninteractive path. Route task requests through the existing orchestrator inbox, preserving project/checkout/start revision and retry identity. A command returns a durable receipt, not a false claim implementation already started.
  5. Connect to one conversation.Resolve the recorded live owner and attach using supported backend capabilities. If attachment is unavailable, durably deliver the request and show the existing conversation route. Reconcile dead owners before starting/resuming, serialize launch races and never steal a live lock. Record actual persistence and transcript-resume limits for each provider.
  6. Build the terminal home screen.Show searchable known/discovered projects, recent/active tasks across repositories, pending decisions, current context and connection status. Provide a direct chat entry and MX Viz shortcut, stable keyboard selection, resize handling and nonblocking discovery. Use the harness for chat and the canonical projection for facts; do not add a model, second state store or workflow engine.
  7. Preserve caller-owned repositories.Integrate the managed/user-owned distinction through refresh, worktree provisioning, unregister and cleanup. Keep dirty files untouched, show the task's selected starting revision and use explicit handling for requested working changes. Audit persistent-home provisioning so it does not re-clone an adopted path simply because old policy expected home-local clones.
  8. Package the installed experience.Distribute verified platform binaries with version-matched runtime assets and adapt runtime validation to packaged installations while retaining source mode. Detect and remember supported harness choice, preserve real trust/authentication requirements, and keep transactional updates and data-preserving uninstall. Ordinary installation must not require a source clone or Rust build.
  9. Integrate the complete multi-repo path.Launch from unrelated directories as well as an example dev root, enter one chat, request work in three differently nested repositories and follow all three tasks through research/implementation and independent outcomes. Switch project filters and open a second terminal while they run; verify bindings and ownership remain unchanged.
  10. Package the internal manager and preserve arbitrary entry.Remove Treehouse from release prerequisites, downloads and TUI guidance. Validate startup from any cwd, optional discovery roots and ordinary multi-repo delegation. Packaged persistent homes use the private-directory path when runtime assets are not a Git checkout.
  11. Connect domain delegation to the same main chat.Expose Phase 05 command help, domain selection/details and routed task submission in the global CLI/TUI. Project selection does not spawn a coordinator; explicit delegation may create one without extra setup or a second main conversation.

Test plan

  • Extend tests/mx-launcher.test.sh, tests/mx-launcher-shell.test.sh and tests/mx-launcher-live-e2e.test.sh for bare workspace entry, explicit shell mode, caller context, remembered harnesses and connection behavior.
  • Extend project-registry Rust tests and add focused discovery/TUI tests using the existing runner pattern; fixtures cover direct/nested roots, spaces, duplicate basenames, aliases, overlapping roots, symlink cycles, linked worktrees, nested submodules, missing paths and remote-free/unversioned folders.
  • Use three fixture repos at different depths. Submit three tasks in one chat, repeat the intake request, change selected project, restart and verify one accepted task per item with correct project/worktree/evidence/delivery identity.
  • Ambiguous repo 2 pauses only its task while repo 1 and repo 3 proceed. Independent capacity or workflow waits preserve the same separation.
  • Race two terminal launches, close the TUI during work, retry an offline request, reconnect with supported attachment and exercise the no-attachment fallback without a second orchestrator or lost inbox record.
  • Snapshot user-owned branch/index/files before discovery, registration, task completion and unregister; verify they remain intact. Test moved/replaced paths and explicit working-change handling.
  • Terminal checks cover keyboard navigation, resize, narrow screens, empty/error/loading views, incremental scan progress and stable selection during updates. Discovery cannot block opening the cached workspace or existing chat.
  • Install, upgrade, interrupted-update recovery and uninstall in isolated platform fixtures without Rust or a source checkout; verify matching assets, retained state, user repositories and documented real harness prerequisites.
  • Run porting acceptance scenarios 19-25 and the relevant A8 cross-repository workload trials; distinguish mocks, real harness checks and unavailable provider capabilities.
  • Package-only startup, persistent homes and multiple repository tasks work without Treehouse, a dev-folder cwd or a runtime Git clone.
  • Launch anywhere, create a scoped coordinator from the same chat, submit direct work alongside it and inspect its children without changing existing task bindings.

Documentation and instruction updates

Rewrite the user entry examples in README and getting started, and update configuration, project lifecycle, launcher help, shell completion and the retained project CLI reference. Document configured roots and local reuse before optional cloning. Keep terminal commands separate from the natural-language multi-task example, and state that one chat owns all repositories.

Definition of done

  • A launch from any directory can find configured nested projects and lets the user reuse existing checkouts without repeated URLs or a Multplx source checkout.
  • One orchestrator conversation coordinates simultaneous work in multiple repositories, and project selection cannot retarget existing tasks.
  • Discovery, registration, intake, reconnection and retry use the existing filesystem owners with truthful identity and no duplicated tasks or orchestrators.
  • The thin TUI and MX Viz agree with canonical task state, remain usable while discovery/work runs, and do not become separate chat or workflow engines.
  • Borrowed repositories remain intact, release packages include required assets, and the supported connection/installation paths have recorded passing evidence.
  • Package-only startup, persistent homes and multiple repository tasks work without Treehouse, a dev-folder cwd or a runtime Git clone.
  • The assigned A11 integration and its focused check above pass with Phase 05.
Integration risk

A project selector alone does not fix flat-clone assumptions, root-bound harness startup or live-owner refusal. Use the shared Phase 02 identity and Phase 04 inbox before exposing commands that promise local reuse and one-chat continuity. Do not claim every provider supports terminal attachment.
