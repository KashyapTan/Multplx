Plan 15 · Multplx

mx-viz — One Live Web View of the Whole System

A read-only, loopback-only web dashboard for the maintainer: mx-viz.sh serve prints a localhost link to a single self-contained page showing every actor, daemon, and the broker's surroundings — reconciled current state, watcher health, headroom and queues, open decisions, backlog, plans, and artifacts — refreshed every few seconds. It is a renderer over the canonical snapshot contract, never a second interpreter of state files, and it can mutate nothing.

Phase 9 (post-port) Effort: Medium Risk: Low Post-port improvement (maintainer request, 2026-07-29)

Overview

Multplx already answers "what is everything doing?" three ways, all terminal-shaped: bin/mx-system-snapshot.sh --json (the canonical read-only structured snapshot, schema mx-system-snapshot.v1), bin/mx-system-view.sh (a human renderer over that snapshot), and bin/mx-status-snapshot.sh (the bounded catchup projection the catchup skill consumes). What's missing is a surface the maintainer can leave open and glance at: one page with everything in flight — which actors are working, blocked, or waiting on a decision; whether the watcher is alive; how much dispatch capacity is left; what's parked in the queues; which plans and artifacts exist for each task — updating itself as the system moves.

mx-viz is that surface. mx-viz.sh serve starts a small loopback-only Node server (the plan 08 server shape, reused nearly verbatim) and prints http://127.0.0.1:4890/. The page polls the server every ~2.5 seconds; the server answers from a cached invocation of the canonical snapshot, re-executing it at most every couple of seconds and only while someone is actually looking. When no client has polled for the idle window, the server exits and frees the port — a forgotten dashboard never becomes a lingering process.

The design discipline that keeps this plan small and safe is borrowed from the two existing snapshot consumers, and it is a hard rule here, not a preference: views never parse system state themselves. mx-system-view.sh's header says it plainly ("this command intentionally does not parse system state itself"), and the plan set records what happens when the rule is broken — a second parser of data/backlog.md is exactly how upstream orphaned backlog bodies. Everything mx-viz shows comes from canonical machine feeds: the system snapshot (extended additively by this plan — see below), mx-headroom.sh --json, and, where later plans have landed, their sanctioned read surfaces (mx-doctor.sh --json, mx-timeline --json). The web layer renders; it never interprets.

Decided · 2026-07-29 — read-only v1

mx-viz v1 is strictly read-only: no control in the page can mutate system state — no nudge, stop, approve, spawn, or drain actions. The server exposes only GET endpoints and its request handler contains no code path that writes inside MX_HOME (its sole writes are its own run record in state/.viz/ at startup/shutdown). This mirrors plan 12's observability-only invariant: a dashboard that can act becomes a second control plane, with authorization, PID-identity safety, and race questions this plan deliberately refuses to take on. Controls, if ever wanted, are a separate maintainer decision with their own plan.

Design tension — a long-lived local server, in a system that avoids them

Plan 04 explicitly rejected an HTTP listener, and plan 08's server is one-shot by design. mx-viz does not contradict either decision: plan 04 rejected HTTP on the write path — a listener whose in-memory state would rival the disk as truth. mx-viz sits entirely on the read path and is fully disposable: kill it at any moment and nothing is lost, because it holds no state that isn't reconstructable from disk (the system's core virtue). The idle shutdown (decided 2026-07-29) keeps even the "forgotten server" cost at zero, and the state/.viz/ run record makes any orphan visible to plan 13's doctor.

Goals & Non-goals

GoalsNon-goals
  • bin/mx-viz.sh (serve / stop / status) + bin/mx-viz-server.mjs, loopback-only, vplan server conventions (port walk, run record, idle timeout, atomic writes).
  • One self-contained vendored page (share/viz/, no CDN) polling /api/state every ~2.5s, re-rendering only when content actually changed.
  • Extend mx-system-snapshot.sh additively with the observability fields it lacks: watcher health, wake-queue depth, dispatch queue, headroom, active vplan reviews, afk flag.
  • Panels: system health strip, tasks board (actors + daemons with reconciled state and signal-tier badges), open decisions, backlog, plans/artifacts browser, and — when the records exist — gate runs, workflow runs, deliveries, upstream drift.
  • Honesty inherited from the system: show snapshot generated age, beacon staleness, and per-task signal tier; never render confident state off stale evidence.
  • Server-side caching so an open dashboard costs at most one snapshot execution per refresh interval, and zero when nobody is polling.
  • No mutations. No POST endpoints, no actions, no writes inside MX_HOME beyond the run record (decided 2026-07-29).
  • No second parser. The web layer never reads state/ or data/backlog.md directly; only canonical feeds are consumed.
  • No daemon: the server runs only while wanted, exits on idle, and nothing in the system depends on it existing (never read for control flow, never a wake source).
  • No non-loopback binding, no auth layer (loopback is the auth boundary), no TLS, no remote/hosted mode (egress).
  • No duplicate review surface: artifacts are browsable and viewable; commenting stays vplan's job.
  • No WebSockets/SSE in v1 — plain polling at a 2–3s cadence is within the accepted latency budget.
  • No bootstrap probe: mx-viz is optional in-repo tooling on the kept node runtime.

Target design in Multplx

Architecture

maintainer's browser                mx-viz-server.mjs (127.0.0.1:4890)          canonical feeds
────────────────────                ──────────────────────────────────          ───────────────
GET /            ──────────────▶    share/viz/ static page (vendored)
GET /api/state   ──poll ~2.5s──▶    cache fresh? ──no──▶ exec mx-system-snapshot.sh --json ──▶ one JSON
                 ◀── {etag,body} ── cache (min refresh MX_VIZ_REFRESH_SECS,          (which itself shells to the
                     304 if same    hash-keyed; refreshed only on demand)             oracle, headroom, backlog lib)
GET /artifact/…  ──────────────▶    read-only static file under data/ or plans/
                                    (path-traversal-proof, no directory writes)
        idle: no request for MX_VIZ_IDLE_SECS ──▶ server exits, run record removed, port freed
  • Pull-through cache, never a poller. The server executes the snapshot only when a request arrives and the cached copy is older than MX_VIZ_REFRESH_SECS (default 2). No client → zero snapshot executions → zero background load. N tabs cost the same as one.
  • Change detection. /api/state responses carry a content hash; the client sends it back (If-None-Match semantics) and gets 304 when nothing changed, so the page re-renders only on real movement and the steady-state cost of an idle system is a few hundred bytes per poll.
  • One JSON, one shape. /api/state returns the extended canonical snapshot verbatim plus a tiny envelope ({server: {started, pid, version}, snapshot: …}). The page's data model is the snapshot schema — there is no viz-private transformation layer to drift.

CLI — bin/mx-viz.sh

usage: mx-viz.sh serve            # start (or report already-running), print the URL
       mx-viz.sh status           # is a server running? port, pid, age, last poll
       mx-viz.sh stop             # verified-identity kill via the run record
       mx-viz.sh --help

behavior:
  serve   → singleton per home: if the run record names a live, identity-verified
            server, print its URL and exit 0 (idempotent). Otherwise launch
            mx-viz-server.mjs, write state/.viz/server.run, print the bound URL.
            Prints the link only — never opens a browser (decided 2026-07-29).
  stop    → reuse the PID-identity primitives (mx-wake-lib.sh pattern, as
            mx-vplan.sh stop does): a dead or reused PID cleans the record and
            never signals the wrong process.

Port selection copies plan 08's decided pattern with a non-overlapping range: default 4890 (MX_VIZ_PORT to override), automatic walk through 4890–4909 when busy (vplan owns 4870–4889), whole-range failure is a hard error naming the range. The bound port lands in the run record.

Server — bin/mx-viz-server.mjs

  • Binds 127.0.0.1 only. Loopback is the entire access-control story, exactly as vplan. Never 0.0.0.0, asserted by test.
  • GET-only. Any other method → 405. There is no handler that writes inside MX_HOME; the read-only guarantee is testable (state-tree hash identical across a full serve/poll/browse session).
  • Routes: / (the page), /assets/… (vendored js/css), /api/state (cached extended snapshot + hash), /artifact/<root>/<relpath> where <root> ∈ data|plans|docs — resolved, canonicalized, and refused unless the real path stays under the corresponding directory (symlink-escape and .. traversal both die with 403).
  • Run record state/.viz/server.run: port, PID, pid-identity, home, started-at. Written at bind, removed on every exit path (idle, stop, signal). A stale record is harmless (identity check fails) and is the doctor's orphan-viz finding once plan 13 lands.
  • Idle shutdown: no request for MX_VIZ_IDLE_SECS (default 1800) → clean exit. An open tab polling every 2.5s keeps it alive indefinitely; closing the tab starts the countdown (decided 2026-07-29).

Snapshot extension — additive fields on mx-system-snapshot.v1

Decided · 2026-07-29 — extend the canonical snapshot, not the view

The observability gaps (watcher, queues, headroom, reviews) are closed inside mx-system-snapshot.sh as additive top-level fields, not by viz-side collectors. One canonical contract stays the single owner of "how system state is read"; every view — terminal and web — gains the fields; and additivity is proven mechanically: the existing mx-system-view/mx-status-snapshot test suites must pass unmodified. Existing fields and semantics are untouched; consumers that ignore unknown fields (all of them — they project by name) are unaffected.

Graceful degradation — the panels contract

mx-viz lands post-port but must be useful the day it lands (plans 01–08 are on main; 09–14 are not). Rule: every panel whose feed is absent renders as absent — no error, no empty-scaffold noise, no fabricated zeros. The snapshot's own omitted[]-style honesty applies: the page distinguishes "0 gate runs" (feed present, empty) from "gate runs not available" (plan 10 not landed). Once plan 13 exists, the health strip additionally offers a doctor summary sourced from mx-doctor.sh --json — invoked on explicit click, not on the poll loop (doctor sweeps are heavier than the snapshot).

Freshness & honesty rules (inherited, not invented)

  • The page always shows when its data was generated, and degrades that indicator visibly as it ages — the system never reports healthy off a stale beacon, and its dashboard doesn't either.
  • State chips carry their tier: a tmux/cmux "working" derived from the busy regex must not look as authoritative as a herdr native event or a validated mx-report line.
  • paths.status_log.last_event renders under a "last event" label, never as current state — the event-log-is-not-truth invariant survives translation to pixels.
  • The dashboard is a convenience view, never truth: nothing in the system reads it, waits for it, or changes behavior because it is or isn't running.

Test plan

(a) Existing tests that must keep passing — unmodified

The entire suite, and specifically the two snapshot-consumer suites (mx-status-snapshot, mx-system-view tests) — they are the mechanical proof that the snapshot extension was genuinely additive. If either changes, step 1 broke the contract.

(b) Existing tests needing changes

The snapshot suite gains additive-field cases (new assertions only — no existing assertion may change). Nothing else.

(c) New tests — tests/mx-viz.test.sh

  • Read-only guarantee (the load-bearing one): hash the entire state tree (excluding state/.viz/), run a full session — serve, poll /api/state repeatedly, browse artifacts, stop — and assert the tree hash is unchanged and no non-GET method is accepted (POST/PUT/DELETE → 405, no write).
  • Loopback only: socket bound to 127.0.0.1, never 0.0.0.0 (same assertion pattern as the vplan test).
  • Port walk: decoy on 4890 → binds 4891 and prints it; whole range occupied → hard error naming 4890–4909, non-zero, no orphan run record.
  • Cache discipline: with mx-system-snapshot.sh replaced by a counting fakebin shim, two polls inside MX_VIZ_REFRESH_SECS execute the snapshot once; a poll after the window executes it again; zero polls → zero further executions.
  • Change detection: identical snapshot content → 304 with matching hash; changed content → 200 with a new hash.
  • Snapshot passthrough: /api/state body's snapshot equals the fake shim's output byte-for-byte — no viz-side reshaping.
  • Path traversal refused: /artifact/data/../../state/…, absolute paths, and a symlink escaping data/ all → 403, nothing served.
  • Idle shutdown: with MX_VIZ_IDLE_SECS=1, an unpolled server exits, removes the run record, frees the port (use plan 6.5's condition-wait helper, no fixed sleeps).
  • Singleton + idempotent serve: second serve against a live server prints the same URL, exits 0, spawns nothing; stop on a stale/reused-PID record cleans the record and never signals the wrong process (PID-identity fixture pattern).
  • Self-containment: the served page and assets contain no external http(s) references.
  • Graceful degradation: a state dir with no gate/workflow/delivery records serves successfully and the payload marks those feeds absent (distinct from empty).
  • Snapshot-extension cases (in the snapshot suite): watcher fields correct against a live-and-fresh fixture, a stale-beacon fixture, and a dead-PID lock fixture (never "alive" off identity mismatch); dispatch/wake queue depths against seeded fixtures; headroom: null + reason when the headroom shim fails — snapshot still exits 0 and every pre-existing field is present.

Risks & open questions

Implementation note · 2026-07-31

The repository's existing snapshot suite is named tests/mx-system-snapshot-view.test.sh, so the additive snapshot cases landed there instead of the plan's stale tests/mx-system-snapshot.test.sh filename. Plans 09 through 14 were already implemented before this work began, so their bounded gate, workflow, delivery, timeline, doctor, and upstream feeds were integrated directly; gate, workflow, and delivery availability remains record-presence-gated so an installed feature with no current run does not produce an empty panel.

Decided · 2026-07-29 — the four shaping decisions

Maintainer decisions, all recorded in porting.md §5: (1) read-only v1 — no mutation surface of any kind; (2) extend the canonical snapshot additively rather than viz-side collectors; (3) idle shutdown — the server exits after no client polls for the idle window; (4) print the link only — never auto-open a browser. Also settled here: the name is mx-viz (hyphenated script per the locked mx- convention — there is no space-separated subcommand style anywhere in the tree), and the port range is 4890–4909.

Risk — scope creep toward a control plane

Every dashboard grows buttons. The read-only decision is enforced structurally, not aspirationally: GET-only routing, no write paths in the handler, and the state-tree-hash test that fails the moment a request mutates anything. Any future control surface must arrive as its own plan with its own authorization design — this plan's server must never be "extended a little."

Risk — snapshot cost under load

The snapshot shells to the oracle and endpoint checks per task; with many live actors a refresh may take seconds, not 0.6s. The cache bounds the damage (one execution per refresh window, only while watched), and the page shows data age honestly, but if refresh latency grows past the poll interval the dashboard lags reality. Acceptable for v1 (2–3s staleness was the stated budget); if it bites, the fix is a --fast snapshot mode (skip endpoint probes) decided then, in the snapshot — never a viz-private shortcut parser.

Risk — additive-schema drift (low)

A future snapshot change could rename a field the page renders. Mitigation is the normal one: the snapshot suite owns the schema, the viz test asserts passthrough (not shape), and the page renders missing fields as absent rather than crashing — the same tolerance every projection wrapper already practices.

Open question — daemon-home drill-down depth

v1 renders daemon_current's bounded per-daemon records (active children, decisions, holds, queued, landed) as cards. A full per-daemon-home drill-down (opening a daemon's own backlog and task set) would mean the snapshot aggregating deeper or viz reading daemon homes directly — the latter is barred by doctrine. Deferred until the bounded cards prove insufficient in practice.

Open question — poll transport later

If 2–3s polling ever feels laggy or wasteful, SSE over the same loopback server is the natural upgrade (server pushes on cache refresh when the hash changes). Deliberately out of v1 — polling is simpler, debuggable with curl, and within the stated latency budget. Revisit only on demonstrated need.
