Plan 18 · Multplx

Cursor CLI and Maintainer-Scoped Overrides

Add Cursor as a fully verified local worker runtime, then make explicit maintainer direction final at every Multplx policy boundary without weakening normal sandboxing, deterministic pipelines, validation facts, or the requirement to authorize each new exception separately.

Phase 12 · Runtime and authority Status: Implemented · 2026-08-09 Risk: High Effort: High Maintainer request · 2026-08-09

Outcome

Multplx will support Cursor CLI through the same verified adapter boundary as Claude, Codex, and Pi.

Normal operation will remain isolated, sandboxed, deterministic, and governed by the selected workflow or delivery path.

When a Multplx policy would refuse an action, the system will identify the exact boundary, explain the consequence, and ask the maintainer for a one-action exception.

An explicit answer will settle that policy decision for the exact action, target, and observed state, and no reviewer, actor, or later pipeline stage may relitigate it without new evidence or a newly encountered boundary.

The central invariant

A maintainer exception changes authority, not reality. It may select a coded alternate path or waive a policy requirement, but it never fabricates a green check, a valid review, an isolated worktree, available credentials, or a capability the host sandbox does not expose.

One exception means one exception

Every grant is single-use and bound to one boundary, one action, one target, and one expected-state fingerprint. A second skipped check, destructive effect, security boundary, remote write, pipeline reorder, or sandbox elevation requires a new explicit maintainer decision.

Part A - Cursor adapter design

Canonical naming and executable discovery

Multplx adapter id: cursor
Preferred real binary: agent
Verified compatibility binary: cursor-agent
Global direct command: multplx cursor [args...]
Activated-shell command: cursor-agent [args...]
Optional agent shim: add only if conflict testing and maintainer review approve it

The generic executable name agent must not become the adapter id because it is ambiguous in state, configuration, logs, and user language.

The launcher captures an absolute real binary before adding shims, exactly as it does for the existing harnesses.

  6. Verify actor turn-end delivery isolated worktreeFind a per-run or project-local hook path that can touch only state/<id>.turn-ended without overwriting a project's committed Cursor configuration or requiring an untracked global user setting.

Verification stop condition

If Cursor cannot supply a collision-safe actor turn-end hook, a bounded primary continuation, or sandboxed isolated writes without a global permission bypass, do not mark it verified and do not expose it in configuration. Record the missing capability and keep current work on a verified runtime.

Part B - Maintainer-scoped override design

Three outcomes, not one generic refusal

ClassMeaningMaintainer authoritySystem response
Policy boundaryMultplx has chosen not to perform an otherwise possible action, such as skipping a stage, merging with failed checks, discarding work, or writing through a normally prohibited path.Final for one exact action after explicit approval.Consume a single-use grant and run the registered alternate.
Integrity assertionA claimed precondition is false or unknown, such as a missing clean verdict, mismatched SHA, live competing lock owner, or non-isolated worktree.May choose a different path but cannot make the assertion true.Offer a coded alternate, such as waive-gate, terminate-and-reacquire, or controlled single-checkout mode, while preserving the factual record.
Capability boundaryThe current process lacks a tool, credential, provider feature, operating-system permission, or host-sandbox capability.May authorize installation, login, elevation, credentialed service use, or operator execution.Perform the authorized setup through the supported mechanism or produce an exact operator handoff, then re-check capability before continuing.

Authorization state machine

policy owner detects boundary
→ describe exact action, target, skipped safeguard, consequence, and smallest alternate
→ if the current maintainer message already explicitly authorizes that exact exception, create one pending grant
→ otherwise record one pending request and stop before mutation
→ maintainer grants or denies that request
→ primary records the decision under the verified session lock
→ boundary owner atomically validates target + action hash + expected-state fingerprint
→ consume once before the exceptional mutation
→ execute only the boundary's registered alternate
→ record outcome and continue through the ordinary pipeline
→ any new boundary starts again with a new request

A proactive instruction counts only when it names the exceptional action, its target, and the safeguard or workflow step being bypassed clearly enough that the consequence is unambiguous.

A generic instruction such as "do whatever it takes", "force it", "finish this", or one earlier exception never grants a later or broader exception.

A changed target SHA, changed worktree state, changed command, changed recipient, changed credentials, changed destructive effect, or expired request invalidates the grant and requires a fresh decision.

Deterministic mechanics

state/maintainer-overrides/
  pending/<request-id>.json
  granted/<request-id>.json
  denied/<request-id>.json
  consumed/<request-id>.json
  stale/<request-id>.json

Required binding fields:
  schema_version, request_id, boundary_id, task_id, project
  action_argv_or_operation, action_digest, target_identity
  expected_state_digest, consequence, requested_at, expires_at
  decision, decided_at, maintainer_words_digest
  consumed_at, outcome, outcome_digest
  • bin/mx-maintainer-override-lib.sh is the one executable owner of schema validation, state transitions, atomic consumption, expiration, target binding, and boundary lookup.
  • bin/mx-maintainer-override.sh exposes inspect, request, grant, deny, consume, and audit commands with literal arguments and no eval.
  • The primary broker alone may convert a direct maintainer answer into a grant, and implementation workers may only request one.
  • Every exceptional caller supplies the current expected-state fingerprint immediately before consumption.
  • Consumption is atomic and happens before the exceptional mutation, so two processes cannot reuse one grant.
  • A consumed grant cannot be restored, copied, inherited by a daemon, forwarded to another task, or carried across a respawn.
  • The append-only journal may mirror request and outcome events for observability, but only the validated private records control execution.
  • No environment variable, command-line --force, or prose-only instruction acts as a generic bypass.

Boundary registry and registered alternates

The implementation begins with a repository-wide refusal inventory and classifies every current policy stop, integrity assertion, and capability failure.

Each policy boundary receives a stable id and exactly one coded alternate owned by the same subsystem.

Example boundaryOrdinary behaviorExceptional alternate after exact approval

Reviewer and pipeline finality

After a valid maintainer decision, later reviewers may report new evidence but may not veto, reopen, or silently undo the same decision. A new factual state or a different boundary creates a new decision; repeated wording about the already-decided boundary does not.

Instruction ownership

  • The always-loaded broker contract keeps only the prime rule: explicit maintainer authority is final for one exact exception, every new exception requires a new decision, and the override skill must be loaded before requesting or applying one.
  • A new internal maintainer-override skill owns classification, evidence requirements, proactive-instruction tests, maintainer-facing wording, and how to record the answer.
  • The existing ask-user-authority skill cross-references the new owner when a maintainer answer changes a normal pipeline boundary.
  • Subsystem scripts own their alternate mechanics and call the shared library for authorization rather than duplicating the state machine.
  • Public operator documentation explains current behavior and inspection commands without copying the complete decision procedure.

Risks and safeguards

Risk - override becomes a master bypass

Prevent wildcard boundaries, standing grants, environment bypasses, grant inheritance, broad task-level force modes, and post-hoc authorization. Bind and consume one exact record before one exceptional action.

Risk - approval laundering

A model must not reinterpret "finish it" as permission to discard data, merge red checks, elevate a command, or write remotely. The proactive-instruction test requires the exceptional action, target, and skipped safeguard to be explicit.

Risk - false finality

The maintainer settles policy, but new facts still matter. A changed object or consequence invalidates the binding and triggers a new decision instead of silently stretching the old one.

Risk - Cursor hook semantics drift

Cursor CLI and hooks are evolving. Pin active evidence to an exact version, ignore unknown additive JSON fields safely, validate required fields, and re-run the live matrix before updating verified facts.

Risk - global Cursor configuration mutation

Do not edit ~/.cursor, persistent sandbox settings, or user permissions during normal launches. Prefer tracked project hooks, per-run files, and explicit setup steps whose scope is visible to the maintainer.

Risk - instruction filename transition

The current uncommitted rename intersects launcher validation, daemon homes, tests, and Cursor auto-discovery. Treat its final filename as a separate prerequisite and do not hide or reverse it inside this feature.

Definition of done

  • cursor is listed as verified only after every required live fact is captured on the installed CLI version.
  • multplx cursor and config/actor-harness=cursor launch a sandbox-enabled Cursor broker or worker through the ordinary Multplx lifecycle.
  • Cursor primary startup, guards, supervision, actor completion, daemon behavior, reporting fallback, interrupt, exit, resume, model selection, and deep-review behavior are tested or explicitly rejected as unsupported.
  • No routine Cursor launch disables sandboxing or grants blanket command approval.
  • Every current Multplx policy refusal is inventoried and either has a registered maintainer-authorized alternate or is classified as an integrity or capability result with a concrete next action.
  • An exact maintainer decision is final for the exact bound action and cannot be vetoed by a reviewer or replayed for another action.
  • Every newly encountered boundary requires a distinct explicit decision.
  • Exceptional outcomes remain truthful, using terms such as waived, discarded, elevated, or maintainer-directed instead of passed or verified.
  • Cross-harness, cross-backend, workflow, validation, delivery, cleanup, daemon, documentation, and full regression suites pass.
  • The implementation preserves the maintainer's separate instruction-file rename without silently reverting or absorbing it.
