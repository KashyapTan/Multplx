Plan 11 · Multplx Port

Workflow Engine — Deterministic Skeleton, Model-Driven Interior

User-defined, repeatable multi-stage workflows the broker can execute like an extension of the maintainer: one shared engine (mx-workflow.sh) enforces stage order, gates, and output contracts from declarative definition files, while the model does the judgment work inside each stage. Includes the create-workflow skill so Multplx can author new workflow definitions interactively with the maintainer.

Phase 8 Effort: High Risk: Medium New feature — no UPDATE_PLAN section (maintainer request, 2026-07-26)

Overview

Multplx's primitives already let the broker emulate any process by hand: spawn an actor with a brief, watch statuses, escalate decisions, run the deep-review gate, hand off delivery. What's missing is a way to make a specific, repeatable process first-class — so the maintainer can define "how I build a feature" (or fix a bug, or run an optimization) once, and then invoke it by name with the broker driving every step the same way, every time.

The motivating example (the maintainer's real feature workflow): ideate back-and-forth until an approach is agreed → produce a spec document → hand the spec to a fresh session that implements it end-to-end → run the code-review pipeline → ship. Each of those stages maps onto a primitive built by plans 03–10; this plan adds the composition layer that sequences them deterministically.

Decided · 2026-07-26 — engine + definitions, not generated scripts

Two implementation shapes were discussed. Rejected: the broker generates a new bash script per workflow that enforces that workflow's sequence. Every generated script would be its own copy of the state machine (drift, N-copies maintenance, untestable surface), and it inverts the port's core safety principle — the model would be authoring its own enforcement layer. Chosen: one shared, hand-written, tested engine (bin/mx-workflow.sh) that interprets declarative definition files (workflows/*.workflow.md). The model — via the create-workflow skill — only ever authors data, which the engine schema-validates before first use. The model proposes; deterministic code decides. Same principle as deep-review.

Design principle

Deterministic skeleton, model-driven interior. A workflow written as free-form prose for the broker to "follow" drifts: stages get skipped, merged, or reordered when context runs long. A fully hardcoded pipeline is too rigid to be user-definable. So the sequence, gates, and output contracts are owned by the engine (the model cannot advance a stage); the content of each stage — the prompt, the charter, the "how I would do it" voice — is markdown the model executes within.

Goals & Non-goals

GoalsNon-goals
  • One engine, bin/mx-workflow.sh + bin/mx-workflow-lib.sh, owning stage sequencing, gates, contracts, and resume.
  • Declarative, schema-validated definitions in workflows/*.workflow.md — versioned, diffable, freely editable by any user of the checkout.
  • Per-stage gate config: approve (maintainer sign-off) or auto (advance when the output contract is met). Configurable on every stage.
  • Free-form run input: one task description (feature idea, bug report, optimization target) — no fixed parameter schema, so one workflow serves many task types.
  • Three stage types: interactive, agent, command — human judgment, model judgment, and deterministic execution each get an honest home.
  • Restart-reconstructable run state under state/<id>.workflow/ — kill anything, the next invocation reconciles. No daemon, no DB.
  • The create-workflow skill: broker-guided interview that emits a definition, validates it, and offers a dry-run.
  • No per-workflow generated scripts (rejected — see decision above).
  • Not a re-expression of deep-review: the gate stays hardcoded with its own trust boundary; workflows call it as a stage.
  • No automation of human judgment — interactive stages pause for the maintainer; the win is that everything between touchpoints self-advances and the run survives days/restarts.
  • No parameter templating in v1 (decided 2026-07-26): the free-form run input covers feature/bugfix/optimization reuse.
  • No new long-running process — the watcher and wake queue Multplx already has carry workflow wakes.

Target design in Multplx

The definition file: workflows/<name>.workflow.md

YAML frontmatter is the machine-enforced skeleton; the markdown body carries one section per stage with the prompt/charter the model receives. The engine reads only the frontmatter for control flow; stage bodies are opaque prompt text to it.

---
workflow_version: 1
name: new-feature
description: Ideate, spec, implement in a fresh session, review, deliver.
stages:
  - id: ideate
    title: Agree on the approach
    type: interactive            # broker <-> maintainer back-and-forth
    gate: approve                # ends only when the maintainer approves
    output: data/{run}/approach.md
  - id: spec
    title: Write the spec document
    type: agent
    executor: broker             # broker writes it inline (or via vplan)
    gate: approve                # maintainer signs off on the spec
    output: data/{run}/spec.md
  - id: implement
    title: Implement end to end
    type: agent
    executor: actor              # spawn a task agent
    fresh_session: true          # never inherits the ideation session
    brief_from: [spec]           # stage artifacts injected into the brief
    gate: auto                   # advance when contract met
    contract: local-commits      # engine-verifiable: commits exist on the task branch
  - id: review
    title: Validation gate
    type: command
    run: bin/mx-deep-review.sh {run} --intent data/{run}/spec.md
    gate: auto                   # exit 0 = validated branch; ask-user findings
                                 # escalate through the gate's own channel
  - id: deliver
    title: Ship it
    type: command
    run: bin/mx-deliver.sh --queue {run}
    gate: approve                # maintainer approves the push (plan 09)
---

## ideate
You are working with the maintainer to converge on an implementation
approach for: {input}
Ask clarifying questions, propose alternatives, push back where you
disagree. Do not start writing the spec until the approach is agreed.
Record the agreed approach in {output}.

## spec
Write a complete end-to-end implementation spec for the agreed
approach in data/{run}/approach.md. ...

## implement
Read data/{run}/spec.md fully before writing code. Implement the
feature end to end exactly as specified; deviations from the spec
must be reported as needs-decision, not silently improvised. ...

Substitution variables are deliberately minimal and fixed by the engine: {run} (the run id), {input} (the free-form task description given at launch), {output} (the stage's declared output path). No user-defined parameters in v1 — the free-form {input} is what makes the same definition serve a feature, a bugfix, or an optimization.

Gates and contracts

  • gate: auto — the engine advances the moment the stage's contract is met. Auto never means unverified: a stage with no verifiable contract cannot be auto (the validator rejects it).
  • gate: approve — contract must be met and the maintainer must approve. Implemented as the existing needs-decision: lifecycle: the engine writes the hold, the watcher escalates it, the maintainer's answer (via the broker) resumes the run. No new escalation mechanism.
  • Contracts the engine can verify deterministically in v1: output file exists and is non-empty; local-commits (task branch head differs from its fork point); command exit 0. The contract vocabulary is closed and validated — extending it means extending the engine, not the definition.

The engine: bin/mx-workflow.sh

mx-workflow.sh validate workflows/new-feature.workflow.md   # schema + contract check, no execution
mx-workflow.sh run new-feature --input "Add dark mode to the settings page"
mx-workflow.sh status <run-id>        # current stage, gate state, artifacts
mx-workflow.sh resume <run-id>        # reconcile + continue after restart/decision
mx-workflow.sh abort <run-id>         # park the run permanently (state kept for audit)
mx-workflow.sh dry-run new-feature    # walk stages, print what each WOULD do

Run state lives under state/<run-id>.workflow/: a snapshot of the definition taken at launch (mid-run edits to the tracked definition never mutate an in-flight run), the free-form input, current stage id, per-stage records (started/finished, artifacts, gate outcome, agent task ids). Everything is plain files; resume re-derives reality the same way the crew-state oracle does — check the recorded facts against what actually exists (does the artifact exist? is the actor task done per reconciliation? did the command's marker land?) and continue from the first unmet stage.

Trust posture

Command execution boundary

command stages and run: fields are arbitrary code execution. Rule, inherited from deep-review's §6.3.1 posture: the engine executes commands only from the repo-tracked definition file's launch-time snapshot — never from any artifact produced mid-run, and never from text an agent stage returned. Definitions are maintainer-authored or maintainer-approved (the create-workflow skill ends with the maintainer reviewing the emitted file before first run). An agent stage that wants a new command in the workflow gets it by the maintainer editing the definition, not by writing it into an artifact.

The create-workflow skill

A skill in .agents/skills/create-workflow/ whose trigger description covers "I want to make a new workflow", "create a workflow for…", "automate my process for…". Flow:

  1. Interview: what are the stages, in order? For each — who does it (you and me talking / an agent / a command)? Fresh session? What artifact proves it's done? Approve or auto-advance?
  2. Draft workflows/<name>.workflow.md — frontmatter from the interview, stage bodies written in the maintainer's described voice ("how I would do it").
  3. Run mx-workflow.sh validate on the draft; fix schema errors before showing it.
  4. Walk the maintainer through the file, then offer dry-run.

The future broker recognizes the request through the normal skills seam (trigger description), with a one-line pointer in example_agents.md's capability inventory — consistent with how every other procedure is wired.

Implementation steps

  1. Write the definition schema spec — docs/workflows.md new: frontmatter fields, the closed stage-type and gate enums, the closed contract vocabulary, substitution variables, workflow_version: 1 semantics. One authoritative owner for the format.
  2. Build the validator in bin/mx-workflow-lib.sh new — parse frontmatter (yaml via the same minimal parsing approach the repo already uses for config; if none exists, a constrained key-set parser — no new runtime dep), enforce enums, reject auto gates without verifiable contracts, reject unknown workflow_version. Pure functions, unit-testable first.
  3. Run record + snapshot + resume — create state/<run>.workflow/ layout, definition snapshot at launch, per-stage record writer, and the resume reconciliation that re-derives current position from recorded facts vs. reality.
  4. command stage executor — subprocess with captured stdout + exit code as truth; contract check; failure parks the run with the captured output attached to the hold.
  5. agent stage executor (broker/headless) — reuse the harness-adapters headless one-shot primitive from plan 10 (claude, codex, pi); stage body + substituted variables as the prompt.
  6. agent stage executor (actor/spawned) — compose stage body + brief_from artifacts into the brief, spawn with fresh_session honored, completion via plan 03's validated status + contract check.
  7. interactive stage + approve gates — park as needs-decision: holds through the existing decision-hold lifecycle; maintainer's answer resumes.
  8. mx-workflow.sh CLI new — validate / run / status / resume / abort / dry-run subcommands over the lib.
  9. Broker wiring — example_agents.md mod: the broker's "run workflow X" verb, and the rule that workflow runs are driven through the engine, never re-improvised from prose.
  10. create-workflow skill new — interview → draft → validate → review → offer dry-run, per the flow above.
  11. Ship the example — workflows/new-feature.workflow.md new: the maintainer's feature workflow as the reference definition and the v1 proving case (build the engine minimally around this one consumer).
  12. End-to-end proof — run new-feature on a real small feature: ideate → spec approved → fresh-session implement → deep-review with the spec as intent → approved delivery via plan 09.

Everything — this plan is purely additive. Specifically unchanged: the crew-state/classify reconciliation tests, decision-hold lifecycle tests, spawn/brief tests, wake-queue tests. The engine consumes those mechanisms; it must not modify them.

(b) Existing tests needing changes

None expected. If wiring the broker verb touches instruction-ownership tests (fm-instruction-owners.test.sh's successor), update the ownership map in the same commit.

(c) New tests

  • tests/mx-workflow-lib.test.sh — valid definition passes; unknown stage type / gate / contract rejected with a clear error; auto gate without a verifiable contract rejected; unknown workflow_version rejected; substitution variables resolved correctly; frontmatter/body stage-id mismatch rejected.
  • tests/mx-workflow.test.sh — stage order enforced (engine refuses out-of-order advance); auto gate advances only when the contract is actually met (artifact missing → no advance); approve gate parks a needs-decision: hold and resumes on the recorded answer; command stage non-zero exit parks the run with captured output; restart-reconstruction — kill mid-run, resume continues from the correct stage; definition-snapshot immutability — editing the tracked definition mid-run does not change the in-flight run; commands executed only from the snapshot, never from a mid-run artifact (the security test); fresh_session stage gets a distinct session/task id from the prior stage; abort parks permanently and run refuses to reuse the id. Risks & open questions

Risk — engine scope creep in bash

A workflow engine can grow conditionals, loops, parallel branches, and sub-workflows until it's a bad programming language in YAML. v1 is a strictly linear stage list — no branching, no parallelism, no includes. If a workflow needs branching, that's a signal the branch belongs inside a stage (model judgment) or in two separate workflows. Revisit only with a concrete case in hand.

Risk — interactive-stage ergonomics

The ideate stage parks and resumes across potentially many maintainer exchanges. The decision-hold lifecycle handles one question cleanly; a long back-and-forth is many holds. Acceptable for v1 (the broker keeps the conversation, the engine only needs the final approval), but watch for friction in the end-to-end proof and adjust there, not speculatively.

Open question — user-local definitions

v1 keeps all definitions repo-tracked in workflows/ (shareable, diffable, satisfies "changeable for all users"). If a private per-user overlay is ever wanted (e.g. ~/.multplx/workflows/), it must still pass the same validator and the same launch-snapshot trust rule. Deferred until someone actually wants it.

Open question — contract vocabulary growth

v1 ships three verifiable contracts (output exists, local-commits, command exit 0). Likely early additions: "tests pass for path X", "PR exists". Each addition is engine code + a validator entry + tests — deliberately not definable in the definition file itself.
