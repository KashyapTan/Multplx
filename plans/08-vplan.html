Plan 08 · Multplx Port

vplan — Plan Artifacts with an In-Page Review Loop

Our replacement for lavish-axi: the broker authors a rich, diagram-heavy HTML plan, serves it on localhost with an injected comment overlay, and the maintainer annotates any element in the page. One confirm click writes the comments into the HTML file itself and shuts the server down — the file is the feedback channel, so there is no persistent daemon, no polling protocol, and no session state to restore.

Phase 5 Effort: Medium Risk: Low UPDATE_PLAN §8.5 + §8.6

Overview

lavish-axi is the upstream author's "AI-agent HTML artifact review system": agents render complex responses as HTML instead of prose, and humans annotate the rendered page directly instead of describing changes in text. The idea is excellent, and firstmate leans on it for exactly the moments that matter — presenting multi-option decisions and structured reports to the captain. Multplx keeps the idea and drops the machinery.

Redesigned · 2026-07-27 (supersedes the original plan 08 draft)

After studying the real lavish-axi repo (kunchenguid/lavish-axi), the maintainer redefined vplan's scope. Rejected: cloning lavish's architecture — a persistent background Node server with session state under ~/.lavish-axi/, a long-polling feedback protocol (lavish-axi poll), agent-presence tracking, a layout-audit gate, Excalidraw diagram editing, and export/share/hosting subcommands. That machinery is what makes lavish heavier than the job needs. Chosen: a one-shot review loop where the served page's comments are written into the artifact file on confirm and the server exits. The original plan 08 draft (input-contract → template renderer) is also superseded: the broker authors HTML directly from a seed template and authoring guide; vplan owns the review loop, not a rendering pipeline.

Design principle

The file is the feedback channel. Lavish keeps feedback in server session state and has the agent poll for it. vplan writes feedback into the HTML file and exits — no daemon to babysit, no protocol to speak, nothing to reconstruct after a crash except a stale PID record. This is more aligned with Multplx's everything-reconstructable-from-disk doctrine than lavish itself is.

Target design in Multplx

The lifecycle

1. AUTHOR   broker discusses the plan in chat, then writes data/<id>/plan.html
            from the seed template, following docs/vplan-authoring.md
            (diagrams via vendored Mermaid wherever they aid understanding)
        │
2. SERVE    mx-vplan.sh review data/<id>/plan.html
            → loopback server on the default port (fallback range if busy)
            → broker tells the maintainer:  "Review at http://127.0.0.1:4870/"
        │
3. ANNOTATE maintainer clicks any element → highlight → types a comment
            → queued in the side panel; repeat freely
            (re-serving a file with existing comments shows them as pins)
        │
4. CONFIRM  one button POSTs the queue → server appends the comments block
            to the actual HTML file → responds "saved" → exits, port freed
        │
5. READ     mx-vplan.sh comments data/<id>/plan.html
            → structured list for the broker → edit plan, mark resolved,
              re-serve for another round or proceed to implementation

Port selection (decided 2026-07-27)

Fixed default port 4870 (MX_VPLAN_PORT to override). When it's busy the server retries upward through a bounded range (4870–4889) and prints whichever port it bound — links stay predictable in the common case, and two concurrent reviews never collide. Binding failure across the whole range is a hard error naming the range, never a silent hang. The bound port is recorded in the state/.vplan/ run record.

Comment persistence format

On confirm, the server appends (or merges into) one machine-readable block before </body>:

<script type="application/json" id="vplan-comments">
[
  {
    "id": "c1",
    "selector": "#delivery-plan > table > tbody > tr:nth-child(3)",
    "anchor_text": "push service owns PR-open",
    "nearest_heading": "Delivery",
    "comment": "Split this into two stages — approval should come before PR-open.",
    "ts": "2026-07-27T21:04:11Z",
    "resolved": false
  }
]
</script>
  • No DOM surgery on the artifact's content. The browser computes the selector, anchor snippet, and nearest heading at click time (it has the live DOM); the server persists JSON verbatim and never parses or rewrites the artifact's markup — the server cannot corrupt the artifact. Writes are atomic (temp + rename).
  • The triple anchor (selector + snippet + heading) keeps comments locatable even if the selector drifts after edits.
  • Resolved comments are flipped to "resolved": true, not deleted (decided 2026-07-27) — the artifact carries its own review history. The SDK renders resolved pins dimmed on later rounds.
  • A <script type="application/json"> block is inert in every browser and invisible in the rendered page — the artifact stays portable, standard HTML.

(a) Existing tests that must keep passing

(b) Existing tests needing changes

The bootstrap test (post-rename successor of tests/fm-bootstrap.test.sh): assert the lavish-axi probe is gone and the vplan self-check passes/fails correctly — same pattern as plan 07's -axi probe removals.

(c) New tests — tests/mx-vplan.test.sh

  • Comment round-trip (golden): serve a fixture artifact, POST a canned confirm payload, assert the saved file gains exactly the expected #vplan-comments block and is otherwise byte-identical; comments subcommand prints the expected parse.
  • Confirm ends the session: after confirm, the server process exits, the port accepts a new bind, and the state/.vplan/ run record is removed.
  • Port fallback: occupy 4870 with a decoy listener → review binds 4871 and prints it; occupy the whole range → hard error naming the range, non-zero exit, no orphan record.
  • Loopback only: the server socket binds 127.0.0.1 (assert via lsof/bind address), never 0.0.0.0.
  • Serve-time injection is non-destructive: while a session is live, the file on disk is unchanged (hash compare); only confirm mutates it, atomically.
  • Merge semantics: confirm on a file with an existing comments block appends new entries and preserves "resolved": true flags; a malformed existing block → refuse with a clear error rather than clobber.
  • Payload validation: a confirm payload missing required fields is rejected (HTTP 400) and writes nothing.
  • Self-containment: the seed template and a generated artifact contain no external http(s) references — vendored assets only, relative paths.
  • Idle timeout: with MX_VPLAN_IDLE_SECS=1, an untouched server exits and cleans its run record.
  • Stale run record: stop on a record whose PID is dead/reused cleans the record and never signals the wrong process (reuse the PID-identity fixture pattern from the plan 04 nudge tests).

Risks & open questions

Risk — concurrent edits during a live review

If the broker edits the artifact while the maintainer has it open, a confirm could merge comments into a file that no longer matches what was annotated. Rule: the run record marks the file as under review, and the broker must not edit it until the session ends (confirm, stop, or idle timeout). The atomic temp+rename write prevents corruption either way; this rule prevents semantic drift. Enforced by instruction plus a doctor check, not a lock — the same soft-enforcement posture as plan 03's write scoping.

Risk — selector fragility across edit rounds

CSS selectors captured in round 1 can dangle after the broker restructures the page. Mitigated by the triple anchor (selector + snippet + nearest heading) — comments reports all three so the agent can locate the target even when the selector misses. Accepted residual risk; lavish's range-anchor machinery is the heavyweight alternative we deliberately dropped.

Open question — pin rendering for text-range comments

Element comments pin cleanly; a text-range comment inside a large element renders its highlight only while the range still exists. v1 falls back to the owning element's pin when the range is gone. Revisit only if it bites in practice.
