Plan 08 / 10

vplan — Standalone HTML Plan-Artifact Module

Multplx's replacement for upstream's lavish-axi, the HTML artifact / plan creator. The module is named vplan, its entry script is bin/mx-vplan.sh, and it is standalone by design: it renders self-contained HTML plan documents from a small plan-input contract, owns its own templates, and is deliberately not folded into the status/finding reporting mechanics.

Phase 5 Effort: Medium Risk: Low UPDATE_PLAN §8.5 UPDATE_PLAN §8.6 (naming)

Overview

Upstream firstmate uses lavish-axi, one of the author's npm-installed -axi tools, as its "structured decisions or reports" surface — but UPDATE_PLAN §8.2 identifies what it actually is: an HTML artifact / plan creator that generates rich HTML plan documents, not a plain structured-report helper. It is a required bootstrap tool today, which means Multplx would inherit a hard npm dependency on someone else's package for a capability we explicitly want to keep and customize.

Per §8.5 we keep the capability but rebuild it as our own separate, self-contained module named vplan, owned by the project. Per §8.6 the naming is decided: the module/product name is vplan, and its script file carries the mx- prefix — bin/mx-vplan.sh, built under that name from the start (never an fm- file renamed later, per §8.7).

Standalone by design (UPDATE_PLAN §8.5)

Unlike the other -axi replacements, vplan is not folded into the status/finding schema work (UPDATE_PLAN §3's write-time-validated status reporting or §6's deep-review findings). Rendering an HTML plan is a different job from validating a status line — keeping them separate lets vplan evolve its own output format and templates without touching the reporting mechanics, and lets the reporting mechanics stay schema-strict without growing a presentation layer.

Two things are in scope to port (§8.5): the plan-input contract (what data goes in — plan metadata, ordered steps/sections, per-step status, links/references) and the HTML generation/templating (what comes out). We reimplement the templating in-repo so we control the markup completely and can customize it freely — we are explicitly not cloning lavish-axi's exact output. Conveniently, we already have a proven target: the plan documents in plans/ (including this very file) are self-contained single-file HTML artifacts with embedded CSS and no external requests. That artifact style becomes vplan's seed template.

Goals & Non-goals

GoalsNon-goals
  • A defined plan-input contract: metadata, ordered steps/sections, per-step status, links/references.
  • bin/mx-vplan.sh: input file in → rendered HTML plan out.
  • Self-contained single-file HTML output: embedded CSS, no external dependencies or network references.
  • Templates owned in-repo, seeded from the plans/ artifact style, freely customizable.
  • lavish-axi fully removed from bootstrap and prose.
  • Fail-closed input validation: malformed input → non-zero exit + stderr diagnostics, no partial output.
  • Cloning lavish-axi's exact markup or feature set — we own the format.
  • Folding vplan into status/finding reporting (§3/§6 mechanics) — explicitly ruled out by §8.5.
  • A web server, live-preview daemon, or any long-running process — vplan is a one-shot renderer.
  • Interactive JS widgets in output — static documents first; scripting only if a future template needs it.
  • Wiring the deep-review gate or backlog items to auto-emit plan artifacts — noted as a future integration, out of scope here.

Plan-input contract (design proposal)

The following JSON shape is a starting-point proposal, not a locked schema — UPDATE_PLAN §8.5 defines the scope ("plan steps, structure, metadata") but leaves the concrete format to us. JSON is proposed first because jq is already the repo's heaviest hard dependency (~305 uses), giving validation and field extraction for free in bash; a markdown-with-frontmatter alternative is sketched below it.

{
  "vplan": 1,                            // contract version, required
  "title": "Owning the Toolbelt",        // required
  "subtitle": "One-paragraph framing.",  // optional
  "plan_num": "07 / 10",                 // optional ordinal label
  "meta": {                              // optional badge row
    "phase": "5",
    "effort": "Medium",                  // Low | Medium | High
    "risk": "Medium",                    // Low | Medium | High
    "source": "UPDATE_PLAN §8.2"
  },
  "sections": [                          // ordered prose/table sections
    { "heading": "Overview", "body_md": "Plain prose. *Minimal* markdown subset." },
    { "heading": "Current state", "table": { "columns": ["File","Role"], "rows": [["bin/x.sh","…"]] } }
  ],
  "steps": [                             // ordered implementation steps
    {
      "title": "Swap the merge call",
      "detail": "Replace gh-axi with gh pr merge …",
      "status": "pending",               // pending | in-progress | done | blocked
      "files": [ { "path": "bin/mx-pr-merge.sh", "action": "mod" } ]   // new | mod | del
    }
  ],
  "links": [                             // references / prev-next navigation
    { "label": "Plan 07", "href": "07-axi-replacements.html", "rel": "prev" },
    { "label": "Plan 09", "href": "09-least-privilege-push.html", "rel": "next" }
  ]
}

Validation rules (fail-closed, enforced by mx-vplan-lib.sh before any output is written): vplan and title are required; steps[].status and files[].action are closed enums; unknown top-level keys are an error (catches typos rather than silently dropping content); every value is HTML-escaped at render time so input can never inject markup or script into the artifact. A missing or invalid field exits non-zero with the offending path printed to stderr — the same write-nothing-and-say-why ethic as UPDATE_PLAN §3's status validation, applied here to documents.

Alternative input format (open, see Risks)

A markdown file with YAML/TOML frontmatter (metadata in frontmatter; ## sections and ordered lists as the body) would be friendlier for hand-authoring but needs a frontmatter parser and a markdown subset definition, and is harder to validate strictly. Proposal: ship JSON first (machine-friendly, jq-validatable — and the broker, the primary producer, generates it anyway); add a frontmatter front-end later as a thin converter if hand-authoring demand appears.

HTML generation / templating

Output is a self-contained single-file HTML document: all CSS embedded in one <style> block, no external fonts, images, scripts, or stylesheets, no http(s):// fetches of any kind — it must render correctly from file:// forever. This mirrors the very artifact style these plan documents use, and the plans/ template (token set: --bg/--surface/--border/--accent…; structures: hero, badges, .steps counter list, callouts, file-impact table, footer nav) is the seed template. Per-plan accent color comes from input (meta or a top-level accent field) with a sane default.

Engine choice — bash+heredoc vs. a small node script. Both are viable; the tradeoff is real and is carried as an open question rather than decided here:

Pure bash + heredoc (+ jq)Small node script
ConsistencyMatches the entire rest of the toolbelt (everything else in bin/ is bash sourcing *-lib.sh); testable by the existing tests/*.test.sh harness with zero new runtime paths.A second implementation language inside bin/ for one tool (though precedent exists: the .mjs command-policy scripts).
Dependency costNone — bash and jq are already required.None in practice — per UPDATE_PLAN §8.3, node stays a runtime dependency anyway for the command-policy scripts, so using it adds no new install burden.
ErgonomicsHeredoc templating is workable but string-escaping HTML in bash is fiddly; loops over steps/sections need care.Template literals, real JSON parsing, and trivial HTML escaping; markdown-subset rendering is much easier if body_md grows.

Lean: bash-first, for consistency with the rest of the toolbelt — jq handles parsing/validation, a small escape helper in mx-vplan-lib.sh handles entity encoding, and heredocs assemble the template. If the markdown-subset rendering or template complexity outgrows bash, the renderer core can move to a node script behind the same mx-vplan.sh CLI without changing the contract. Flagged as an open question for the maintainer below.

CLI

mx-vplan.sh --input <plan.json> --out <path.html> [--template <template.html>]

  --input     plan-input JSON (use '-' for stdin)
  --out       output HTML path; parent dir must exist; written atomically
              (temp file + rename) so a failed render never leaves a partial artifact
  --template  optional template override; defaults to templates/vplan/default.html

exit 0  rendered
exit 1  invalid input (contract violation; offending field path on stderr)
exit 2  usage / IO error

Test plan

Runner: bin/fm-test-run.sh (to become mx-test-run.sh).

(a) Existing tests that must keep passing

  • tests/fm-bootstrap.test.sh — the full required-tool matrix keeps passing once lavish-axi leaves the fake list; no other bootstrap behavior changes in this plan.
  • vplan is additive and standalone, so no other existing suite (tests/fm-session-start.test.sh, tests/fm-teardown.test.sh, the reporting/classifier suites) is touched — that isolation is itself the §8.5 design property, and an unchanged pass across the suite is the evidence.

(b) Existing tests needing changes (and why)

  • tests/fm-bootstrap.test.sh — remove lavish-axi from the fm_fake_exit0 fakebin seed (it would otherwise mask a stale probe) and add a negative assertion that bootstrap output contains no MISSING: lavish-axi line under any matrix row. This is the same file Plan 07 edits for the other three probes; land as one coordinated change.

(c) New tests to write

  • tests/mx-vplan.test.sh —
    • Golden-file rendering: a fixed fixture input (covering metadata, both section variants, all four step statuses, all three file-action pills, and prev/next links) renders to byte-identical golden HTML. Deterministic output is a hard requirement: no timestamps, locale-dependent formatting, or environment leakage in the artifact; a second render of the same input is byte-equal to the first.
    • Input validation: each contract violation — missing title, missing vplan version, invalid status enum, invalid files[].action, unknown top-level key, unparseable JSON — exits non-zero, names the offending field path on stderr, and writes nothing to --out (no partial artifact after a failed render).
    • Output self-containment: the rendered artifact contains no external http(s):// references — no linked stylesheets, scripts, fonts, or images (relative hrefs between sibling plan documents are the allowed exception). Also asserts input text is entity-escaped: a fixture containing <script> and quote characters in every string field must appear escaped in the output, never as live markup.

Risks & open questions

Open question — templating engine (maintainer decision)

Pure bash+heredoc+jq vs. a small node script. The plan leans bash-first for toolbelt consistency, but node stays a runtime dependency regardless (UPDATE_PLAN §8.3: the .mjs command-policy scripts), so the node option costs no new install burden and buys much easier escaping/templating. Decision needed by step 2; the CLI contract is engine-independent either way.

Open question — input format second front-end

JSON is the proposed contract (broker-generated, jq-validatable). Whether a markdown-frontmatter front-end for hand-authoring is worth adding is deferred until real hand-authoring demand exists; if added, it converts to the JSON contract rather than becoming a second schema.

Open question — how rich is body_md?

The proposal allows a minimal markdown subset inside section bodies (emphasis, inline code, lists). The exact subset — and whether step detail fields get the same treatment — is unspecified. Start with the smallest set the seed template needs and grow deliberately; a large subset is the strongest argument for the node engine.

Risk — scope creep toward a reporting system

Low overall risk (additive module, no consumers in the critical loop), but the one real hazard is drift: once vplan exists, it will be tempting to route status updates or review findings through it. §8.5's boundary is the guardrail — vplan renders plan documents; the schema-validated reporting path (§3) and the deep-review gate (§6) never depend on it. The docs and the AGENTS.md rewrite state this boundary explicitly.
