Plan 09 / 10

Least-Privilege Push — Agents Never Hold Remote Credentials

Split "the work is done" from "the work leaves the machine." Actors commit locally only — the local commit is the verifiable "artifact exists" signal for a done task. A separate, non-agent process with its own service credentials owns git push and PR-open, and it fires only after validation passes and/or the maintainer approves.

Phase 6 Effort: Medium Risk: Medium UPDATE_PLAN §2

Overview

UPDATE_PLAN §2 states the principle plainly: actors (firstmate's crewmates) "should never hold remote write credentials — this isn't a workaround for an org policy, it's the correct shape regardless." The two halves of the design, verbatim from §2:

  • An actor commits locally only — "no remote permission needed, and it's our verifiable 'artifact exists' signal for a done task."
  • A separate, non-agent process with its own service credentials owns the actual git push / PR-open step, "triggered only after validation passes and/or the [maintainer] approves."

Today, delivery in firstmate is agent-adjacent: whichever session runs fm-pr-merge.sh uses whatever GitHub credentials are ambient in that environment, and the push that precedes a PR happens from inside the crewmate's own session with the crewmate's own token. A prompt-injected or simply confused agent can therefore push anything, anywhere its token reaches, at any time. The fix is structural, not behavioral: take the capability away. Agent processes run with no push-capable credential at all (read-only token or none), so "the actor decided to push early" becomes "the actor cannot push," enforced by the credential boundary rather than by prompt discipline.

This plan designs the concrete mechanism: a new mx-push-service (working name; entry script bin/mx-deliver.sh) that runs outside any agent session — invoked directly by the maintainer, or by a credentialed launchd/cron context — reads a queue of validated branches (state/<id>.ready-to-push records written by the deep-review gate, plan 10), performs the push and gh pr create, and records the resulting PR URL back into task state where the existing watcher machinery picks it up.

UPDATE_PLAN §6.4 confirms this is the load-bearing end of the gate design: the local pipeline deliberately stops at "a clean, validated branch committed locally — nothing has left the machine," and delivery "ties directly into §2 (least-privilege push): the crewmate never pushes." §6.4 also notes the consequence we inherit for free: the system becomes "egress-safe and push-guard-compatible by construction" — the single outbound git push goes through one normal, approved, human-or-service-controlled path.

Goals & Non-goals

GoalsNon-goals
  • Actor and daemon processes hold zero push-capable credentials — enforced by environment construction, not prompts.
  • Local commit on the task branch is the canonical "artifact exists" signal for a done task.
  • A non-agent mx-push-service owns push + PR-open, gated on a validated .ready-to-push record and the maintainer's approval chain.
  • Push refuses if the branch head moved after validation (approved-SHA pinning).
  • PR URL flows back into task state so the existing PR-check/poll watchers work unchanged.
  • Merge goes through plain gh (plan 07's gh-axi→gh swap), invoked from the same credentialed non-agent context.
  • Reimplementing the deep-review gate itself — plan 10 owns validation; this plan only consumes its verdict.
  • A push-proxy remote or any no-mistakes-style git proxy (explicitly rejected in UPDATE_PLAN §6.5).
  • A long-running push daemon with in-memory state — the queue is on disk and every run is restart-reconstructable, per firstmate's core design virtue.
  • Local-only delivery (fm-merge-local.sh's fast-forward path) — it never touches a remote and needs no credentials; it survives as-is (renamed).
  • GitLab support — the fork is GitHub-only (UPDATE_PLAN §8.1 deletes glab).

Current state in firstmate

Firstmate already has strong merge discipline but no push-side credential separation. The pieces (all paths verified against the checkout):

  • bin/fm-pr-merge.sh — the one sanctioned path to merge a task's PR. Parses the canonical PR URL via fm-pr-lib.sh, records pr=/pr_head= into the task meta first (so teardown's landed-check has a reference), then merges via gh-axi: gh-axi pr merge "$PR_NUMBER" --repo "$PR_OWNER/$PR_REPO" ... (line 84). GitHub-only; refuses non-GitHub providers. Defaults to --squash.
  • bin/fm-pr-check.sh — records a PR-ready task: validates and stores one canonical pr=<url> plus the forge's exact pr_head=<sha>, then atomically arms a static merge poll. Task/PR data live in a private sidecar, never interpolated into shell source.
  • bin/fm-pr-poll.sh — the static watcher program for a validated PR poll sidecar: emits exactly one merged line when the PR merges and stays silent otherwise (including on every error, so a failed lookup can never read as a merge). Reads GitHub via gh (and GitLab via glab — the branch plan 07/§8.1 deletes).
  • bin/fm-pr-lib.sh — shared URL parsing/validation (task-id validity, canonical URL, owner/repo/number extraction, provider tagging).
  • bin/fm-push-transition-lib.sh — shared owner of the watcher's native push-transition escalation (handle_push_transition): how the watcher reacts when a crewmate's work transitions to pushed/PR state. Sources fm-wake-lib.sh, fm-classify-lib.sh, fm-backend.sh, fm-transition-lib.sh.
  • bin/fm-merge-local.sh — the local-only delivery path: after captain approval, fast-forwards the project's default branch to the crewmate's fm/<id> branch. Refuses diverged branches. Never touches a remote.

The gap: nothing separates who can push from who does the work. The crewmate pushes its own branch with ambient credentials; fm-pr-merge.sh runs wherever it's invoked with whatever token is in scope. There is no on-disk record of "validated and approved at SHA X" that delivery is conditioned on.

1. Actors commit locally only

An actor's definition of done for a ship task becomes: a clean, validated branch committed locally in its worktree. The local commit is the verifiable "artifact exists" signal — the broker (and teardown's landed-work check) can confirm the artifact by inspecting the local repo, with no remote round-trip and no remote permission. The deep-review gate (plan 10) ends at lint with exactly this state, per UPDATE_PLAN §6.4.

2. The ready-to-push queue

The deep-review gate, on a passing run, writes one record per task — the queue is just files in state/, restart-reconstructable like everything else:

# state/<id>.ready-to-push        (written by mx-deep-review.sh; consumed by mx-deliver.sh)
worktree=/path/to/worktree
branch=mx/<id>
approved_sha=<head SHA at the moment validation passed>
base=main
gate_run=state/<id>.gate/            # pointer to the gate's run record (findings, rounds)
approval=pending|approved            # flipped by the maintainer's decision (or standing +yolo)
title/body source                    # PR title + body assembled from the gate's summary + risk line
  • approved_sha is the contract. It pins exactly what was validated. If the branch head moves after validation (actor kept working, anything), the record is stale and the service refuses — the branch must be re-validated.
  • approval plugs into the existing authority chain. A gate run that parks ask-user findings surfaces them as needs-decision: to the maintainer (UPDATE_PLAN §6.3); only after the maintainer approves (or a standing +yolo auto-approves) does the record flip to approved. The push service never interprets findings itself — it only checks the flag.

3. mx-push-service — the non-agent deliverer

Entry script bin/mx-deliver.sh new (with shared logic in bin/mx-deliver-lib.sh new). It is a plain script, not a daemon: each invocation scans state/*.ready-to-push, delivers eligible records, and exits. Two sanctioned invocation contexts, both outside any agent session:

  • Maintainer-invoked: the maintainer runs mx-deliver.sh [<id>] from their own shell, with their own credentials, as the explicit "ship it" act.
  • Credentialed scheduler context: a launchd (macOS) / cron job whose environment carries the service credential, delivering any record that is already approved. This gives unattended delivery without ever putting the credential in an agent's environment.

Per record, the service:

  1. Re-verifies eligibility: record parses, approval=approved, and git -C <worktree> rev-parse HEAD still equals approved_sha. Any mismatch → refuse loudly, mark the record stale, escalate to the maintainer; never "push whatever is there now."
  2. Refuses agent ambience: aborts if agent-session markers are present in its own environment (e.g. CLAUDECODE=1 and the other harness env markers) — a belt-and-braces check that it is not being run from inside an actor/broker/daemon session.
  3. Pushes: git push origin <branch> — a normal push to the real remote through the approved credential path. No force-push, no proxy remote (§6.5's rejection).
  4. Opens the PR: gh pr create with the deterministically-assembled title/body from the gate's run record (summary + risk line — assembled by code, not by an agent prompt, mirroring upstream no-mistakes' deterministic PR assembly noted in §6.2).
  5. Records the result back into state: feeds the PR URL through mx-pr-check.sh (today's fm-pr-check.sh), which validates it, records pr=/pr_head=, and arms the static merge poll — so the entire existing watcher chain (poll → merged line → push-transition handling in mx-push-transition-lib.sh → teardown) works untouched. The .ready-to-push record is archived to state/<id>.delivered.

Why this is the correct shape (not a policy workaround)

UPDATE_PLAN §2 is explicit: "this isn't a workaround for an org policy, it's the correct shape regardless." The blast radius of any agent failure — prompt injection, hallucinated "done", runaway loop — is capped at the local worktree. Nothing an agent can do results in remote writes, because no agent process possesses the capability. §6.4 adds the corollary: the single outbound push goes through "the normal approved remote path a human/service account controls — not an AI-driven force-push to a proxy remote."

5. What happens to the merge path

fm-pr-merge.sh → bin/mx-pr-merge.sh mod keeps its exact contract (record pr=/pr_head= into meta before merging; squash default; refuse non-GitHub; no --repo/-R in extra args) but swaps gh-axi pr merge for plain gh pr merge (plan 07) and is documented as a push-service-context command: it runs where the service credential lives, on the maintainer's merge approval — never inside an agent session. fm-merge-local.sh → mx-merge-local.sh is untouched by this plan (local-only, credential-free by nature).

Risks & open questions

Risk — credential hygiene is the whole ballgame

If the service credential ever lands in a file an agent can read (repo, worktree, shared env file), the separation is theater. The credential must live only in the maintainer's shell session or the scheduler context's credential store, and the test suite's env-leak assertions guard the other direction (agent env never reaches the service's subprocesses). Review every state/doc write the service makes to ensure no token material is ever serialized.

Open question — read-only token vs. no token for actors

UPDATE_PLAN §2 allows either ("read-only token or no token"). No token is simplest but breaks authenticated reads (private-repo fetch, PR-status reads an actor might legitimately need). A fine-grained read-only token restores those but is one more secret in agent scope. Per-project choice, maintainer to decide; default proposal: no token, add read-only per project only when a real need appears.

Open question — delivery latency and the scheduler

Maintainer-invoked delivery is zero-infrastructure but means approved work waits for a human keystroke. The launchd/cron context removes the wait for already-approved records but adds a standing credentialed job on the machine. UPDATE_PLAN §2 says "triggered only after validation passes and/or the [maintainer] approves" — that and/or is a real policy knob (auto-deliver on gate-pass vs. always require explicit approval), possibly per-project alongside the existing delivery-mode/autonomy registry. Maintainer decision; default proposal: explicit approval required until trust is established.

Open question — where does the branch get pushed from?

The service pushes from the actor's worktree path recorded in the .ready-to-push record. That worktree must still exist and be at approved_sha at delivery time — which orders delivery before teardown. Alternative: the gate could bundle the validated commits (e.g. git bundle) into state so delivery survives early teardown. Extra machinery; deferred unless worktree-lifetime coupling proves painful in practice.

Risk — two sources of push-transition truth during migration

Until every project is on the new flow, the watcher may see pushes from both old-style (agent-pushed) and new-style (service-pushed) tasks. mx-push-transition-lib.sh's classification is agnostic to the pusher, so this is a doc/expectations issue rather than a code one — but call it out in the migration notes so a legacy agent push isn't mistaken for a service failure.

Deviations

The implemented mx-push-transition-lib.sh handles native runtime agent-state transitions, not remote Git pushes. The credentialed service therefore feeds the existing watcher through mx-pr-check.sh as designed, while the transition library receives only a clarifying comment and no behavior change.

The service pushes approved_sha:refs/heads/<branch> instead of resolving the local branch name again at push time. This is a stricter form of the planned normal non-force push: remote non-fast-forward protection remains, and a concurrent local branch advance can never widen the approved payload.
