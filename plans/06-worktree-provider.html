Plan 06 · Multplx Port

Worktree Provider — Keep Treehouse

Treehouse stays: pinned v2.0.1, SHA-256-verified, functionally untouched. This plan carries it through the port properly — the rebrand rename of its installer and call sites, an unconditional bootstrap requirement now that the orca backend is gone, and the integration guarantees the gate, teardown, and doctor depend on.

Phase 4 Effort: Low Risk: Low UPDATE_PLAN §1 + §8

Overview

Firstmate separates the session provider (where an agent's terminal lives — tmux, cmux, herdr after plan 01's pruning) from the worktree provider (where an agent's checkout lives). The worktree provider is treehouse (kunchenguid/treehouse): a pooled set of disposable git worktrees with a locked on-disk claim table and process/lease-based in-use detection, so a worktree is reused across tasks (keeping node_modules and build caches warm) but never recycled out from under a live task or a daemon's durable lease.

Multplx keeps it. It's the one upstream tool worth keeping deliberately: the pool-reuse value-add is real, the lease/reclaim concurrency logic is the genuinely hard part and it already works, and the integration is small and well-contained (four call-site scripts plus a pinned installer). Unlike the -axi wrappers plan 07 replaces, treehouse is pinned and checksum-verified — upstream cannot change what we execute without us changing the hash.

Decided · 2026-07-26 · reaffirmed 2026-07-27

Keep treehouse. UPDATE_PLAN contradicted itself — §1 said "treehouse → build our own" while §8 said "treehouse — kept as-is. It's the one upstream tool we like and want to keep using. No change." The maintainer resolved it in §8's favor on 2026-07-26 and reaffirmed on 2026-07-27, at which point the build-our-own designs (a no-pool variant and a pooled mx-worktree with lease logic) were removed from this plan entirely — they live in git history if ever needed. This plan is now solely about carrying treehouse through the port correctly.

Current state in firstmate

Treehouse is installed via the pinned installer (bin/fm-install-treehouse.sh): it downloads the exact v2.0.1 release asset per platform (linux/darwin, amd64/arm64), enforces a bounded 15 MB download ceiling, verifies a hardcoded per-platform SHA-256, and runs a post-install version check — never a floating package-manager latest. Target design in Multplx

Functionally identical to today. The changes are carriage, not behavior:

  • Rename only (rides plan 02's sweep): bin/fm-install-treehouse.sh → bin/mx-install-treehouse.sh; env knobs FM_TREEHOUSE_RETURN_LOCK_RETRIES / FM_TREEHOUSE_RETURN_LOCK_RETRY_WAIT_SECS / FM_TREEHOUSE_CI_* → MX_TREEHOUSE_*. Call sites move with their host scripts (mx-spawn.sh, mx-teardown.sh, mx-home-seed.sh, mx-bootstrap.sh). Pin, SHA table, bounded download, settle loop, landed-work refusal, lease check: byte-for-byte.
  • Bootstrap simplification: the "only require treehouse when the backend needs it" conditional existed for orca (the one backend owning its own worktrees). Orca is deleted in plan 01, so all kept backends (tmux, cmux, herdr) need treehouse — the probe and treehouse_supports_lease() check become unconditional, removing a dead branch.
  • Downstream guarantees, stated as contracts: plan 10's gate prompts assert "you are in an isolated git worktree; its .git is a pointer file" — treehouse worktrees supply that isolation. Plan 09's push service treats a local commit as a durable artifact — teardown's landed-work refusal is what makes that true, and it stays untouched. Plan 13's doctor reads treehouse leases vs. live tasks for its orphan-worktree check.
  • Upstream watch: treehouse is an external pinned dependency, so plan 14's docs/upstream.md record lists it alongside the firstmate fork point (repo URL + pinned version); bumping the pin is an ordinary reviewed change that updates the installer's version + SHA table.
Emergency fallback (documented, not built)

If treehouse's release assets ever become unavailable, the degraded-mode fallback is plain git worktree add/remove per task — losing pool reuse (cold node_modules/build caches) but nothing else, since the worktree's existence is reconstructable state via git worktree list. Recorded here so an outage has a known answer; no code is written for it.

Implementation steps

  1. Rename the installer. bin/fm-install-treehouse.sh → bin/mx-install-treehouse.sh mod — rename + var-prefix only; keep the v2.0.1 pin, per-platform SHA-256 table, 15 MB bounded download, and post-install version check byte-for-byte.
  2. Carry the call sites through the rebrand. As part of plan 02's sweep, the treehouse logic in mx-spawn.sh, mx-teardown.sh, mx-home-seed.sh, and mx-bootstrap.sh mod moves unchanged; env knobs → MX_TREEHOUSE_*; log/comment vocabulary → maintainer/actor/daemon.
  3. Make the bootstrap requirement unconditional. Remove the backend-conditional guard around the treehouse probe and treehouse_supports_lease() mod — with orca gone there is no backend that doesn't need it. Update the bootstrap test accordingly.
  4. Register treehouse in the upstream record. Add it to docs/upstream.md (plan 14's Phase-0 record): repo URL, pinned version, where the SHA table lives — so pin bumps are tracked, reviewed changes.
  5. Verify end-to-end. Run the worktree suite under the renamed scripts, then one real round-trip on a treehouse-backed backend: actor spawn (get → settle → work) and daemon home-seed (get --lease) → teardown (return --force with the landed-work check exercised).

Keeping treehouse still defines how the broker provisions isolation and how daemons hold durable leases, so those responsibilities must remain current after the port.

  • example_agents.md: update spawn, daemon provisioning, and teardown references to the final mx-* paths and retain the isolation, lease, and unlanded-work safety rules.
  • docs/architecture.md, docs/configuration.md, and docs/upstream.md: document treehouse's provider role, pin, lease capability, and relationship to session providers.

  • Documentation verification: run bin/mx-doc-audience-check.sh and verify that no broker instruction names a pre-rebrand treehouse caller.

Risks & open questions

Risk — upstream availability

Treehouse is a binary controlled by the upstream author. Mitigations in place: exact version pin, hardcoded per-platform SHA-256, bounded download, post-install version check — upstream cannot silently change what we execute. Residual risk is release assets disappearing, for which the documented plain-git worktree fallback above is the emergency answer, and plan 14's upstream watch is the early warning.

Resolved — no open questions

The keep decision is final (2026-07-26, reaffirmed 2026-07-27) and the former open questions (build triggers, pool-ownership timing) were removed with the build-our-own material. If treehouse ever has to be replaced, the four call-site scripts above are the entire integration surface — that containment is itself part of why keeping it is safe.
