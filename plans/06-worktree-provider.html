Overview

Firstmate separates the session provider (tmux, herdr, zellij, cmux, orca — where an agent's terminal lives) from the worktree provider (where an agent's checkout lives). The worktree provider is treehouse, an external binary by the upstream author (kunchenguid/treehouse), pinned at v2.0.1 with SHA-256-verified release archives. Every backend except orca (which owns its own worktrees) depends on it.

What treehouse actually is, per UPDATE_PLAN §1: "a pooled set of disposable git worktrees, a locked on-disk state file tracking which are claimed, and process/lease-based 'in use' detection so a worktree isn't recycled out from under a live task." Its real value-add is pool reuse: a recycled worktree keeps warm node_modules and build caches across tasks. Its hard part is the reuse-vs-safe-reclaim logic — §1 is explicit that "durable leases for secondmates with no live process vs. safe-to-recycle orphans... is the one part not to shortcut." (In Computer vocabulary: durable leases for daemons with no live process.)

The strategic question for Computer: treehouse is upstream-author-controlled, like the -axi toolbelt we are replacing (plan 07). But unlike the -axi wrappers, it is a real tool with genuinely hard concurrency logic, it is already pinned and checksum-verified (no floating-latest risk), and firstmate's integration with it is small and well-contained. That is why §8's "keep" stance is defensible even though §1's "own it" instinct is also right long-term.

This plan documents where treehouse touches firstmate today, fully specifies both the keep path and the build path (including the two build sub-options), and recommends a sequencing that gets Computer standing first and revisits ownership later as an optional module.

Current state in firstmate

Treehouse is installed either manually (curl -fsSL https://kunchenguid.github.io/treehouse/install.sh | sh, the hint printed by fm-bootstrap.sh) or via the pinned CI installer. The pinned installer (bin/fm-install-treehouse.sh) downloads the exact v2.0.1 release asset for the platform (linux/darwin, amd64/arm64), enforces a bounded download ceiling (15 MB), verifies a hardcoded per-platform SHA-256, and runs a post-install version check — never a floating package-manager latest.

Runtime touchpoints:

  • Bootstrap probe + lease-capability check — bin/fm-bootstrap.sh probes command -v treehouse and additionally reports treehouse as MISSING when the installed version lacks treehouse get --lease support (function treehouse_supports_lease(), ~line 528; the check only fires when the resolved backend actually requires treehouse — every backend except orca).
  • Task spawn — bin/fm-spawn.sh sends treehouse get into the new pane and runs a 60-iteration settle loop waiting for the pane's cwd to move from the project into the acquired worktree, then validates the result via validate_spawn_worktree. A known WSL/tmux race (transient stale pane_current_path) is handled here and regression-tested by tests/fm-spawn-worktree-settle.test.sh.
  • Daemon home leasing — bin/fm-home-seed.sh acquires a fresh firstmate home via treehouse get --lease --lease-holder <id> (function acquire_treehouse_home()), which durably leases the worktree until teardown or rollback returns it via treehouse return. This is the "durable lease with no live process" case §1 warns about.
  • Teardown / return — bin/fm-teardown.sh returns the worktree via treehouse return --force, with a landed-work safety check first (return hard-resets the worktree, so unlanded commits must be refused) and a bounded retry loop for the transient .git/index.lock "File exists" race (FM_TREEHOUSE_RETURN_LOCK_RETRIES, default 3).

Target design in Computer

PATH K  Keep treehouse (per §8) — decided 2026-07-26

Treehouse stays exactly as it is: external binary, pinned v2.0.1, SHA-256-verified via the installer. The only changes are the mechanical rebrand renames from plan 08's mx- sweep (UPDATE_PLAN §7.4):

  • bin/fm-install-treehouse.sh → bin/mx-install-treehouse.sh; internal FM_TREEHOUSE_CI_* variables → MX_TREEHOUSE_CI_*.
  • Treehouse call sites move with their host scripts: mx-spawn.sh, mx-teardown.sh, mx-home-seed.sh, mx-bootstrap.sh. Env knobs FM_TREEHOUSE_RETURN_LOCK_RETRIES / FM_TREEHOUSE_RETURN_LOCK_RETRY_WAIT_SECS → MX_TREEHOUSE_*.
  • No functional change: same get / get --lease --lease-holder / return --force command surface, same settle loop, same landed-work refusal, same lease-capability bootstrap check.
Why K — the deciding rationale

Path K costs near-zero effort, keeps the pool-reuse value-add (warm node_modules/build caches) and the hard lease logic that already works, and — critically — does not put a high-effort concurrency rewrite on the port's critical path. The remaining downside (a dependency on an upstream-author binary) is mitigated by the pin + checksum: upstream cannot change what we run without us changing the hash.

PATH B  Build our own (per §1) — rejected for the port; retained for reference

B1 — no pool (simple). Per §1: "Easy to reimplement if we don't need pool reuse: plain git worktree add/remove per task, no pool at all."

  • A small bin/mx-worktree.sh with two verbs: claim <id> runs git worktree add on a fresh path (e.g. worktrees/<id>) and prints it; release <id> runs git worktree remove (after the same landed-work check teardown does today).
  • No state file, no leases, no reclaim logic — the worktree's existence is the state, reconcilable from git worktree list. This matches firstmate's "everything reconstructable from disk" virtue.
  • Cost: loses treehouse's entire value-add — every task cold-starts node_modules and build caches. For JS/TS-heavy projects that is minutes per task, multiplied across the fleet.

B2 — pooled reuse with lease logic (the real replacement). This is the option §1 says is "worth real design time", and its reclaim logic is "the one part not to shortcut." Sketch:

bin/mx-worktree.sh <verb>                     # the pooled provider
  claim   [--lease --lease-holder <id>]       # acquire: reuse a free pooled worktree, else git worktree add
  release [--force] <path|id>                 # return to pool: reset --hard + clean, mark free
  status                                      # dump pool state (debugging / bearings)
  reclaim                                     # sweep: recycle orphans, never live claims or durable leases

state/worktree-pool.json                      # locked on-disk claim table
  { "worktrees": [ { "path": "...", "state": "free|claimed|leased",
      "holder": "<task-or-daemon-id>", "pid": 12345,
      "lease": true|false, "claimed_at": "<iso8601>" } ] }
  • Locked state file. All mutations of state/worktree-pool.json go through firstmate's existing perl-Fcntl lock helper (fm-lock-lib.sh → mx-lock-lib.sh) so two concurrent claims cannot hand out the same worktree.
  • In-use detection is process/lease-based, not trust-based. A claimed entry records the claimer's PID; reclaim treats a claimed worktree whose PID is dead as an orphan (safe to recycle). A leased entry (--lease) is durable: it is held by a daemon that legitimately has no continuously-live process (daemon homes survive process restarts), so reclaim must never recycle it — only an explicit release by holder id frees it. This claimed-vs-leased split is exactly the reuse-vs-safe-reclaim logic §1 flags as the part not to shortcut, and it mirrors today's treehouse get vs. treehouse get --lease --lease-holder distinction that fm-spawn.sh and fm-home-seed.sh already rely on.
  • Recycle = reset, keep caches. release runs git checkout/reset --hard + a selective clean that preserves ignored build artifacts (node_modules, build caches) — that retention is the entire point of the pool. Same landed-work refusal as today's teardown before any reset.
  • Command-surface compatibility. Keep the verbs close enough to treehouse's (claim/get, release/return) that mx-spawn.sh, mx-teardown.sh, and mx-home-seed.sh only swap the binary name and flag spellings, not their logic (settle loop, retry-on-index.lock, rollback paths all survive unchanged).

Decision

Decided · 2026-07-26

Path K wins — treehouse is kept as-is for the port: it honors §8's explicit "kept as-is" decision, costs only the rename, and keeps the port's critical path free of a hard concurrency build. Building our own (Path B) is rejected for the port; a pooled mx-worktree (B2) remains only a possible far-future optional module — if ever green-lit, the treehouse call sites are already isolated behind four scripts, so swapping the provider would be a contained change validated against a working system instead of on paper.

B1 was likewise rejected as a destination (it discards the pool's value-add); it stays documented only as an emergency fallback if treehouse ever becomes uninstallable. This resolves the §1/§8 conflict in §8's favor — not just for sequencing, but as the port's decision of record.

(c) New tests to write

  • tests/mx-worktree.test.sh (far-future Path B2 only) — asserts:
    • claim/release round-trip: claim yields a real distinct worktree path recorded as claimed in the pool file; release resets it and marks it free; a second claim reuses it (ignored build artifacts survive the recycle).
    • lease not recycled under a live process: a claimed entry whose PID is alive is never touched by reclaim; a leased (durable) entry is never touched by reclaim even with no live process — only explicit release by holder id frees it.
    • orphan reclaim: a claimed (non-lease) entry whose PID is dead is swept back to free by reclaim.
    • concurrent claim safety: N parallel claim calls against a smaller pool never hand the same worktree to two callers (lock contention test via the pool-file lock).

Risks & open questions

Decided · 2026-07-26 — the §1 / §8 contradiction

UPDATE_PLAN §1 said "treehouse → build our own"; UPDATE_PLAN §8 said "treehouse — kept as-is. It's the one upstream tool we like and want to keep using. No change." The maintainer confirmed §8's answer: keep treehouse. Rejected alternative: Path B (build our own, per §1) — off the port's roadmap entirely; pooled B2 survives only as a possible far-future optional module.

Decided · 2026-07-26 — B2 status (formerly the timing-trigger question)

B2 is not on the roadmap, so no trigger is scheduled — it is at most a possible far-future optional module. The candidate triggers recorded while this was open (treehouse upstream going stale/unavailable, pool semantics treehouse can't support, post-port capacity) remain the only sensible reasons to ever reopen it.

Risk — B2's reclaim logic is the dangerous part

§1 is explicit: the durable-lease vs. orphan-reclaim distinction is "the one part not to shortcut." Getting it wrong recycles a daemon's home out from under it (data loss) or leaks worktrees forever (pool exhaustion). This was the single strongest argument for Path K, and it carried the 2026-07-26 decision: we keep treehouse's working lease logic, and any far-future replacement would be built and tested entirely off the critical path.

Risk — upstream dependency under Path K

Path K keeps a binary controlled by the upstream author. Mitigations already in place: exact version pin (v2.0.1), hardcoded SHA-256 per platform, bounded download, post-install version check — upstream cannot silently change what we execute. Residual risk is availability (release assets disappearing), for which B1 exists as a documented emergency fallback.

Risk — orca asymmetry

Orca owns its own worktrees and bypasses this whole decision. Any future B2 work must preserve that asymmetry (bootstrap only requires the provider for non-orca backends), or orca spawns will start failing a probe they never needed.
