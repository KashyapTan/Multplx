Plan 16 · Multplx

Human Documentation Revamp

Replace the inherited Firstmate landing page with a concise, Multplx-native README shaped like Xpdite; add a real documentation entry point and onboarding path; audit every human-facing Markdown page against the behavior delivered by Plans 01–15; and retire migration-era prose from the active documentation surface without changing agent-runtime contracts.

Phase 10 · Final productization Effort: Medium–High Risk: Medium Documentation-only plan · 2026-07-31 Completed · 2026-08-01

Overview

Plans 01–15 changed Multplx from a Firstmate port into its own system, but the human documentation did not receive the same final product pass. The current README.md still has the Firstmate README's structure, hero treatment, long feature list, and community chrome. The repository diff confirms it was edited in place rather than redesigned, and the top badges still link to the upstream author's X account and Discord server.

The detailed documentation is much stronger than the landing page: the repository has 29 human-facing Markdown pages under docs/, classified as operator, maintainer-architecture, or maintainer-verification material. What it lacks is a human information architecture. There is no docs/README.md, no focused getting-started guide, no reading path by audience, and no concise bridge between the public README and the authoritative detail.

Plan 16 closes that gap. It uses Xpdite's README as a formatting reference - centered identity, useful badges, clear “Why” and “Core Features” sections, a short getting-started path, a Mermaid architecture diagram, and a documentation table - while keeping every claim, command, link, and visual specific to Multplx.

Decided · Xpdite is the layout model, not a content template

Reuse Xpdite's visual rhythm and section hierarchy, not its product claims, providers, install commands, screenshots, or app language. Multplx remains an agent coordination distribution. The existing assets/banner.png stays available as the hero visual; this task does not invent a new logo. Release and demo badges appear only when they have real Multplx targets.

Documentation boundary

This plan covers the public README, CONTRIBUTING.md, all 29 human-facing Markdown pages under docs/, and the completed migration prose at the repo root and in plans/. It does not rewrite AGENTS.md, CLAUDE.md, .agents/skills/, docs/supervision-protocols/, or docs/vplan-authoring.md; those are agent-runtime contracts. The vendored firstmate/ tree remains excluded from Multplx documentation ownership.

Target README

Xpdite-inspired structure

  1. Centered identity. Multplx name or existing banner, one sentence of positioning, and a restrained for-the-badge row for License, Stars, and Platform. Add Release only when a real Multplx release target exists.
  2. Primary navigation badges. “Get Started”, “Documentation”, and “Contributing”, linking to docs/getting-started.md, docs/README.md, and CONTRIBUTING.md.
  3. Multplx. Two short paragraphs: what it is, who it is for, and the maintainer/broker/actor/daemon model.
  4. Why Multplx. Five or six user outcomes: one conversation, parallel isolated work, durable supervision, explicit human authority, safe delivery, and restart-proof state.
  5. Core Features. Six to eight final-product bullets covering the capabilities delivered by Plans 01–15, not a chronological port inventory.
  6. Getting Started. Requirements, clone, select one verified harness, run it from the repo, make a first request, then point to the canonical guide for backend and delivery setup.
  7. Architecture Diagram. One Mermaid flow showing maintainer → broker → actors/daemons → isolated worktrees, with supervision/snapshot and deep-review/delivery as supporting flows. Replace the current fragile ASCII diagram.
  8. Documentation. A compact table linking the docs index, getting started, architecture, configuration, delivery, backends, operations, and contributing.
  9. Contributing, License, Sponsor. Match Xpdite's close. Reuse the maintainer's sponsor link only if it is still intended for Multplx.

Implementation steps

  1. Freeze the documentation inventory mod — generate the exact non-agent surface list from docs/documentation-audiences.json, record each file's audience and authoritative owner, and create a temporary audit checklist in task evidence rather than a new tracked manifest.
  2. Build the two human entry points first new — add docs/README.md and docs/getting-started.md. These establish the reading paths and the canonical setup owner before the README is shortened.
  3. Rewrite README from a clean outline mod — implement the Xpdite-shaped structure above, reuse only valid Multplx assets and links, replace ASCII with Mermaid, remove upstream social chrome, and route details to the new docs entry points.
  4. Audit current operator pages against the implementation mod — check every command against script headers/--help, every feature against current code and tests, every backend label against its current support level, and every cross-reference against the one-owner rule.
  5. Separate mechanism from evidence new — create docs/verification/guards.md, move current dated proof from guard mechanism pages, and leave focused pointers. Keep existing supervision and backend verification owners for their own evidence.
  6. Retire completed migration prose delete — distill unique current facts from UPDATE_PLAN.md, firstmate_dependencies.md, and plans/porting.md; update owners where necessary; then remove those files and their inventory entries. Do not create a duplicate archive.
  7. Refresh the plan index mod — rename its framing from a future Firstmate port to the Multplx implementation ledger, explain that Plan 6.5 makes seventeen artifacts across numbered Plans 01–16, add the Phase 10 card, and link Plans 15 ↔ 16.
  8. Update documentation classification and navigation mod — register new pages and removals in documentation-audiences.json, keep documentation-audiences.md as the policy pointer, and add appropriate “Back to docs index” links without filling every page with repeated navigation chrome.
  9. Run structural and semantic verification — execute the documentation audience check, local-link validation, stale-vocabulary/social-link searches, git diff --check, HTML validation, and a rendered README review at desktop and narrow widths.
  10. Review the complete diff as one documentation system — re-check audience, owner, current relevance, evidence destination, and unique safety facts for every changed page after all fixes. Confirm no product behavior, agent contract, or exact safety invariant changed accidentally.

Content checks

  • The agent process is never told to run gh auth login or hold a write-capable token.

  • Every backend is labeled consistently: tmux reference; Herdr and cmux experimental; Codex App not selectable.
  • Dated proof lives only in maintainer-verification pages, except a short current verification pointer.
  • Deleted migration pages leave no broken links in current Markdown or plan navigation.

Rendered review

  • Preview README.md with GitHub-compatible Markdown: badges resolve, the banner fits, Mermaid parses, tables do not dominate, and code blocks remain copyable.
  • Check the README and docs index at desktop and narrow/mobile widths.
  • Open Plan 16 and the updated plan index locally; verify navigation, table overflow, heading hierarchy, and no clipped content.
  • Review the final README beside Xpdite: the relationship should be visible in format, while no Xpdite-specific product content should have crossed over.

Ordering and dependencies

  • Runs after Plans 01–15. The documentation must describe the final behavior, so Plan 16 is the closing productization phase.
  • Entry points precede cleanup. Add the docs index and getting-started owner before shortening README or deleting stale setup prose.
  • Fact distillation precedes deletion. A migration page is removed only after every unique current fact and regression pointer has a verified owner.
  • Evidence moves after owner review. Do not relocate live-validation sections until the destination verification page and backlinks exist.
  • README is reviewed last as a product page. Its content is drafted early, but the final pass happens after the detailed docs are accurate so links and claims cannot lead ahead of their owners.

Risks & safeguards

Risk — polishing stale facts

Copy-editing can make an outdated command look more authoritative. Every changed behavior claim must be checked against code, script help, current tests, or maintained verification before wording is improved.

Risk — README becomes another manual

Xpdite's structure is useful because it creates clear layers. Keep the README persuasive and scannable; move operational nuance to the docs index and specific owners.

Risk — losing safety rationale while shortening

Guard, credential, worktree, and decision-hold pages may look repetitive because they reinforce safety boundaries. Apply the one-owner rule carefully: remove duplicate mechanics, but preserve one authoritative rationale and a focused pointer at each genuine risk point.

Risk — historical references are mistaken for stale product claims

docs/upstream.md must continue naming Firstmate and fm-* paths because it drives the review-and-reimplement workflow. Searches are review tools, not blind replacement commands.

Definition of done

  • The README is recognizably Multplx, follows the agreed Xpdite-like structure, contains no upstream X/Discord feature or community link, and points to valid Multplx destinations.
  • docs/README.md and docs/getting-started.md provide a coherent path from curiosity to a safe first run.
  • All 29 existing human-facing docs/*.md pages have a recorded semantic disposition: changed, moved, retained after verification, or retired.
  • Stable mechanism prose and dated validation evidence live in their classified owners with no lost safety fact.
  • Completed migration Markdown is removed only after fact distillation; the HTML plan set remains the historical record.
  • The plan index presents Plans 01–16 plus 6.5 accurately and links Plan 15 to Plan 16.
  • bin/mx-doc-audience-check.sh, local-link checks, stale-link searches, HTML validation, and git diff --check pass.
  • A final rendered review confirms the README, docs index, and plan index are readable on desktop and narrow screens.
  • No agent-runtime contract or product behavior changed as a side effect of the documentation work.
