Plan 14 · Multplx

Upstream Sync — Don't Fork and Forget

The moment Multplx forks, kunchenguid/firstmate keeps evolving without us. This plan makes staying informed a deliberate, cheap, recorded process: a tracked fork-point record, a read-only diff/triage script (mx-upstream-diff.sh), and an upstream-sync workflow definition for the plan-11 engine — review-and-reimplement, never git merge, run on a cadence the maintainer chooses, with an explicit retirement path when triage stops paying for itself.

Phase 9 (post-port) Effort: Low Risk: Low Post-port improvement (maintainer request, 2026-07-27)

Overview

Multplx is a hard fork. The port renames everything (fm-→mx-, the full vocabulary sweep of plan 02), deletes whole subsystems (X-mode relay, glab, zellij/orca backends, grok/opencode harnesses, the no-mistakes pipeline, the -axi toolbelt), and — per porting decision #8 — removes the vendored firstmate/ folder entirely when the port is done. From that day forward, upstream bug fixes stop arriving. Silently.

That matters because the port deliberately keeps several subtle mechanisms verbatim — the "What NOT to rebuild" list: the reconciliation oracle (fm-crew-state.sh lineage), the watcher lock, the liveness beacon, the turn-end guard, the wake queue. These are exactly the kind of code where upstream will keep finding and fixing rare race conditions, and exactly the kind of code where Multplx would never notice it inherited a latent bug. A fork that never looks back accumulates upstream's already-fixed bugs as its own unknown unknowns.

At the same time, a git-level sync is off the table forever. Every file is renamed, every identifier is reworded, and whole directories upstream still patches don't exist in the Multplx tree. An upstream commit will never apply cleanly — not with git merge, not with cherry-pick, not with patch -p1. The only honest sync model is review-and-reimplement: read what upstream changed, decide whether the change matters to a mechanism Multplx kept, and if so reimplement it against the mx- equivalent as an ordinary task through the normal deep-review gate.

This plan builds the smallest apparatus that makes that sustainable: (1) a tracked fork-point record so we always know exactly which upstream commit Multplx diverged from and which upstream commit was last reviewed; (2) a review procedure backed by a read-only script that fetches upstream into a scratch directory and filters the diff through a subsystem relevance map; (3) the procedure packaged as a workflow definition for the plan-11 engine, so every sync run is stage-gated, resumable, and recorded rather than improvised. And because upstream divergence only grows, the design includes an explicit, recorded way to retire the sync when triage cost exceeds value — a decision, not a lapse.

Time-critical — one step belongs to the port, not to this plan

The fork-point commit SHA of the vendored firstmate/ copy must be captured before that folder is deleted (porting decision #8 removes it at end of port). Once firstmate/ is gone, reconstructing the exact divergence point means archaeology against upstream history. The capture is a five-minute step — see Implementation step 1 — and the port's Phase 0 checklist and definition of done in plans/porting.md should reference it. Everything else in this plan is genuinely post-port; this one step is not.

  • Ported fixes land as ordinary Multplx tasks with the normal deep-review gate — no special fast lane for "it came from upstream".

Target design in Multplx

Part 1 — The fork-point record: docs/upstream.md

One tracked markdown file, human-readable prose around a machine-parseable header block (same constrained key-set style the workflow frontmatter uses — no new parser dependency):

---
upstream_repo: https://github.com/kunchenguid/firstmate
fork_point: <sha>        # upstream commit the vendored firstmate/ copy matched
last_reviewed: <sha>     # upstream commit covered by the most recent completed sync run
status: active           # active | retired
retired_reason:          # required when status: retired
---
  • fork_point is written once, during the port (step 1 below), and never changes. It is the anchor for the very first sync run's diff range.
  • last_reviewed advances only through the workflow's final, maintainer-approved record stage — never by hand-edit convention, and mx-upstream-diff.sh refuses to advance it any other way. This is what makes "did we look at that change?" answerable from the repo.
  • status: retired is the recorded off-switch (see "When to stop" below). When set, mx-upstream-diff.sh exits with a clear "upstream sync retired: <reason>" message and does nothing — the decision is visible, not a silent lapse.

Below the header, the file carries the subsystem relevance map — the triage filter, maintained as a table:

Map maintenance rule

The map's default for unmapped paths is flag, not skip. Every sync run that flags an unmapped path ends by adding that path to the map (relevant / irrelevant / deleted) so the next run is quieter. The map converges; the triage cost goes down over time, not up — until upstream refactors, which is the divergence signal the "when to stop" section watches for.

Part 2 — The review procedure

bin/mx-upstream-diff.sh is the deterministic half of the procedure. Contract:

mx-upstream-diff.sh --out <dir>              # full run: fetch, diff, filter, report
mx-upstream-diff.sh --since <sha> --out <dir> # override the from-SHA (default: last_reviewed)
mx-upstream-diff.sh --record-reviewed <sha>   # the ONLY writer of last_reviewed (workflow record stage)
mx-upstream-diff.sh --status                  # print record-file state; exit 3 if status: retired
  • Fetch, read-only: shallow-clone (or fetch into a cached scratch clone of) the upstream repo under the scratch directory. The script never writes anything outside --out and its scratch clone dir — hard rule, enforced by test. The Multplx working tree is not touched.
  • Diff range: last_reviewed..upstream/HEAD (first run: fork_point..upstream/HEAD). Emits per-commit log --stat plus per-file diffs into <out>/.
  • Filter: classify every touched path against the relevance map. Commits touching only deleted/irrelevant paths are listed one-line-each in a "skipped mechanically" appendix; commits touching any relevant path get their full diff in the report body; unmapped paths land in a "needs mapping" section.
  • Report: a single report-input.md — the raw material for triage: upstream HEAD SHA, commit list grouped by relevance, full diffs for relevant changes, the unmapped list, and counts.

The judgment half is triage. For each relevant change, exactly one classification:

ClassMeaningWhat happens
portA bug fix (or safety tightening) in a mechanism Multplx keptReimplement against the mx- counterpart, in Multplx vocabulary, as an ordinary task — brief cites the upstream commit; the change goes through the normal deep-review gate like any other code. Upstream's regression test is reimplemented too.
skipA feature, a change to a subsystem Multplx deleted, or a fix to behavior Multplx intentionally replacedOne line in the triage report with the reason. Recorded, so the same commit is never re-triaged.
flagUnclear whether Multplx wants it — design-level change, or touches a mechanism Multplx modified (plans 03–05 additive changes), or an unmapped pathEscalates to the maintainer in the workflow's review stage; the maintainer's ruling converts it to port or skip, and updates the relevance map if a mapping was missing.

Part 3 — Delivery as a workflow definition (the showpiece)

The whole procedure ships as workflows/upstream-sync.workflow.md for the plan-11 engine — which is exactly the composition the engine was built for: deterministic fetch, model-judged triage, human gate, fresh-session implementation, deterministic record. Sketch (final field names must match the shipped docs/workflows.md schema):

---
workflow_version: 1
name: upstream-sync
description: Review upstream firstmate changes since the last sync; port relevant fixes.
stages:
  - id: fetch
    title: Fetch upstream and build the filtered diff report
    type: command                      # deterministic; exit code is ground truth
    run: bin/mx-upstream-diff.sh --out data/{run}/upstream/
    gate: auto
    output: data/{run}/upstream/report-input.md
  - id: triage
    title: Classify each relevant change (port / skip / flag)
    type: agent
    executor: broker                   # headless one-shot turn; structured report out
    gate: auto
    output: data/{run}/triage.md       # every commit: class + one-line reason;
                                       # flags carry the question for the maintainer
  - id: review
    title: Maintainer reviews the triage
    type: interactive                  # broker walks the maintainer through triage.md;
    gate: approve                      # flags get ruled; approved port list is the output
    output: data/{run}/approved-ports.md
  - id: port
    title: Implement the approved ports
    type: agent
    executor: actor
    fresh_session: true                # implementer never inherits triage context
    brief_from: [review]               # approved-ports.md + upstream diffs in the brief
    gate: auto
    contract: local-commits            # one commit per approved fix; each goes through
                                       # the normal deep-review gate before delivery
  - id: record
    title: Record the new last-reviewed upstream SHA
    type: command
    run: bin/mx-upstream-diff.sh --record-reviewed data/{run}/upstream/head-sha
    gate: approve                      # the SHA advances only on maintainer sign-off
---
  • Stage 1 (fetch) is a command stage: fully deterministic, no model in the loop, exit code + declared output are the contract. Zero approved changes is a valid, fast path — the report says so and the maintainer approves straight through to record.
  • Stage 2 (triage) is where the model earns its keep: reading diffs of subtle bash and judging "is this a fix to a mechanism we kept?" The output is a structured report, not code — the model proposes, nothing executes.
  • Stage 3 (review) is the human gate. Nothing gets reimplemented without the maintainer having seen the classification. This is also where relevance-map updates get ruled.
  • Stage 4 (port) honors fresh_session — the implementing actor gets the approved list and the relevant upstream diffs as its brief, one task per approved fix, each landing as an ordinary commit through the normal deep-review gate. (v1 workflows are linear, so one actor session works the approved list sequentially; if a sync ever approves a large batch, the maintainer can instead spawn the fixes as independent ordinary tasks and let the workflow's port stage cover the remainder — noted under open questions.)
  • Stage 5 (record) is the only path that advances last_reviewed, and it sits behind an approve gate. A run that dies mid-way leaves the SHA untouched — the next run simply re-covers the same range.
Cadence — maintainer-chosen, no daemon

Run mx-workflow.sh run upstream-sync --input "monthly sync, <date>" monthly or quarterly — manually, or nudged by whatever external reminder the maintainer already uses (calendar, cron reminder, a note in the weekly review). Explicitly no new daemon, poller, or webhook: the sync is a workflow run like any other, and the existing watcher/wake machinery carries it once launched. If upstream announces a security-relevant fix out of band, run it off-cadence — the diff range self-adjusts.

When to stop — retirement is a recorded decision

Honest expectation

Upstream divergence only grows. Every Multplx phase and every upstream release makes the trees less comparable; eventually upstream refactors the very files the relevance map points at, and triage cost exceeds the value of the occasional inherited fix. That point is expected, not a failure. When a couple of consecutive sync runs produce mostly flags and no ports — or a single triage takes longer than reimplementing a fix from scratch would — the maintainer should downgrade to watching upstream release notes only, and record it: set status: retired (with retired_reason) in docs/upstream.md. From then on mx-upstream-diff.sh refuses to run (clear message, distinct exit code), the workflow's fetch stage fails loudly rather than silently skipping, and anyone reading the record file sees when and why the fork stopped looking back. Retirement is reversible the same way — flip the status, and the diff range picks up from the still-recorded last_reviewed.

Implementation steps

  1. Capture the fork-point SHA — during the port, before firstmate/ is deleted mod — Add to the port's Phase 0 checklist and definition of done in plans/porting.md: record the upstream commit SHA that the vendored firstmate/ copy corresponds to. If the vendored copy carries no git metadata, determine it by cloning kunchenguid/firstmate to a scratch dir and finding the commit whose tree matches the vendored content (diff candidate commits against firstmate/; if local modifications exist, record the nearest matching ancestor plus a note listing the local deltas). Write it into docs/upstream.md new immediately — the record file can exist from Phase 0 even though everything else here is post-port.
  2. Write the relevance map mod — Fill docs/upstream.md's map table from the port's actual outcome: every kept mechanism with its mx- counterpart, every plan-01 deletion as deleted, the plan 03–05-modified files marked "port with care", tests included. Source of truth for the mappings is the plan set itself (01 for deletions, 02 for renames, 03–05 for modified-but-kept).
  3. Build bin/mx-upstream-diff.sh new — Fetch/diff/filter/report per the contract above. Hard write boundary: scratch clone dir + --out only. Reads the record header (repo URL, last_reviewed/fork_point, status); honors retired with a distinct exit code; --record-reviewed is the sole writer of last_reviewed and refuses to move it backwards. Filtering is pure path-glob matching against the map — no model in this script, ever.
  4. Author workflows/upstream-sync.workflow.md new — The five-stage definition above, validated with mx-workflow.sh validate before first use. Stage bodies carry the triage charter (the port/skip/flag rubric, verbatim), the review-stage walk-through script, and the port-stage brief template (cite upstream commit, reimplement in Multplx vocabulary, reimplement the regression test, normal deep-review gate).
  5. Write the tests new — tests/mx-upstream-diff.test.sh (see test plan) plus the workflow-definition validate fixture; register both in the mx-test-run.sh family map in the same commit.
  6. First live sync run as validation — Run the workflow for real against whatever upstream has accumulated since the fork point. This proves the fetch boundary, the filter quality, the report ergonomics, and the record-stage gate on real data — and its output doubles as the first entry in the sync log. Expect the relevance map to gain a few entries; that's the map-maintenance rule working.

(b) Existing tests needing changes

Only the naming-test allowlist addition above (same commit as the files that need it, with the reason in the commit message). Nothing else: no ported mechanism is modified by this plan.

(c) New tests

  • tests/mx-upstream-diff.test.sh — run under bin/mx-test-run.sh, house pattern (tests/lib.sh, fakebin shims, deterministic git fixtures — the "upstream" is a local fixture repo, so no network in tests):

Register the new test file in the mx-test-run.sh family map in the same commit; --check-coverage must pass.

Risks & open questions

Risk — the capture step gets missed

If the port finishes and firstmate/ is deleted without the fork-point SHA recorded, the first sync run's diff range has no anchor. Recovery is possible (git history of this repo still contains the vendored tree at the pre-deletion commit; match it against upstream history from a scratch clone) but tedious. Mitigation: the step lives in the port's Phase 0 checklist and its definition of done, and docs/upstream.md is created at Phase 0 so its absence is visible for the whole port.

Risk — triage misclassification

The model could classify a subtle fix as skip, silently losing it. Mitigations already in the design: the map defaults unmapped paths to flag (never silent), the maintainer reviews the entire triage report — including the skip lines with reasons — at the approve gate, and skips are recorded per-commit so a wrong call is auditable and correctable at the next run. The residual risk is accepted: this process is a net gain over the alternative, which is reviewing nothing.

Risk — reimplemented fix diverges from upstream's intent

Reimplementing against renamed, partially modified code can miss the point of the original fix — especially in files plans 03–05 extended. Mitigations: the relevance map marks those files "port with care"; the port-stage brief requires reimplementing upstream's regression test, which encodes the bug independent of the fix's shape; and the normal deep-review gate applies. Never weaken a kept invariant to make an upstream patch "fit" — if a fix appears to require that, it's a flag, not a port.

Open question — batch size in the port stage

v1 workflows are strictly linear, so the port stage is one fresh actor session working the approved list sequentially. Fine for the expected steady state (a few small fixes per quarter). If a sync ever approves a large batch, the better shape may be the workflow ending at the review stage and the fixes fanning out as independent ordinary tasks. Decide when it actually happens — do not pre-build parallelism into the workflow engine for this (plan 11's scope-creep risk stands).

Open question — exact fork-point identification if the vendored copy was locally modified

If firstmate/ drifted from any single upstream commit before Phase 0 (stray local edits), the record stores the nearest matching ancestor plus a delta note. Whether any such drift exists is checked, not assumed, at capture time. This is a record-keeping detail, not a design fork — carried here so the capture step doesn't silently paper over it.

Open question — retirement threshold

"A couple of consecutive low-value runs" is a heuristic, not a rule. Deliberately left to maintainer judgment — the design's job is only to make the decision cheap to take and impossible to take silently (status: retired + reason in the tracked record).
