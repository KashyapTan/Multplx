Plan 03 / 10

Validated Status Reporting — Enforce the Schema at Write-Time

Give actors a validated write path for status events: a new bin/mx-report shell wrapper that rejects any state outside the closed enum before a single byte is written, and a JSON-schema-validated MCP report_status tool for harnesses that support MCP. Both paths still append to the same state/<id>.status event log; the downstream reconciliation oracle is untouched.

Phase 3 Effort: Medium Risk: Low UPDATE_PLAN §3

Overview

Multplx's status channel is an append-only event log at state/<id>.status, deliberately never trusted as current-state truth. bin/mx-actor-state.sh is the reconciliation oracle that re-derives real state from the authoritative sources (an attributed validation run step, then the pane busy signal), and bin/mx-classify-lib.sh classifies each event line against a documented verb vocabulary (done:, needs-decision:, blocked:, failed:, working:, paused:, resolved:). That architecture is sound and is explicitly on UPDATE_PLAN's "do not rebuild" list.

The actual gap: the vocabulary is enforced nowhere on the write side. The generated brief instructs the task agent to hand-write status lines with a raw shell append — echo "{state}: {one short line}" >> state/<id>.status (see bin/mx-brief.sh, the "Report status by appending one line" rule in both the delivery and scout scaffolds). Nothing validates that line before it lands. A typo'd verb (blocekd: need help) or a free-form line is parsed by status_line_verb, matches no known verb, and is silently bucketed downstream as an unclassified no-verb heartbeat — no escalation, and crucially no error back to the model, so the agent believes it reported and the broker never hears the intended signal.

The fix, verbatim from UPDATE_PLAN §3: add validation upstream of the write, not after it. Two validated write paths, one enum:

  • bin/mx-report — a thin wrapper actors call instead of hand-writing to the status file. It validates --state against the closed enum working|paused|blocked|needs-decision|done|failed|resolved (the full Multplx classifier vocabulary — decided 2026-07-26, see below) client-side; on invalid input it writes nothing, exits non-zero, and prints the valid options to stderr — so the model sees the failure in its own tool output on the same turn and can retry immediately.
  • MCP report_status tool — for harnesses that support MCP: a real JSON-schema-validated tool. The harness itself rejects a malformed call before it ever executes, which is stronger enforcement than a shell wrapper's own checking.

This is additive to the existing event-log model, not a replacement. Both paths write the exact same line grammar to the exact same file; mx-actor-state.sh and the whole reconciliation logic do not change — they just receive better-validated input.

Target design in Multplx

The closed enum, in one place

Decided · 2026-07-26
The closed enum is Multplx's full classifier vocabulary, verified in bin/mx-classify-lib.sh: working|paused|blocked|needs-decision|done|failed|resolved. UPDATE_PLAN §3's five-state enum was incomplete and is extended to match the real vocabulary per maintainer decision — paused is the expected-idle pause verb (a deliberate external wait, distinct from blocked) and resolved closes an open keyed decision; both are actor-written verbs the wrapper must accept, or actors would be forced to hand-append exactly the lines the brief tells them never to hand-write. The rejected alternative — keeping the §3 five-state enum literally and leaving paused/resolved on the raw-append path — is dropped. The broker-side transfer verb maintainer-held stays out of the enum: it is never actor-written.

Both write paths validate against the same seven-state list, defined once (a small shared constant in mx-report that the MCP server reuses — see step 2).

Path 1 — bin/mx-report (shell wrapper, works on every harness)

usage: mx-report --id <task-id> --state <state> --message "<one short line>" [--key <slug>]

  --state   one of: working | paused | blocked | needs-decision | done | failed
            | resolved   (closed enum — the full classifier vocabulary)
  --key     optional keyed-decision slug; emits the existing
            "<state> [key=<slug>]: <message>" grammar (mx-classify-lib's
            status_open_decisions contract), slug charset [A-Za-z0-9._-]

behavior:
  valid    → append "<state>: <message>" (or keyed form) to state/<id>.status; exit 0
  invalid  → write NOTHING; exit non-zero; stderr:
             "mx-report: invalid state '<input>'. Valid states: working, paused,
              blocked, needs-decision, done, failed, resolved"

Design points:

  • Fail-loud on the same turn. The whole point is that the model sees the rejection in its own tool output immediately and retries with a valid state — instead of the malformed line vanishing into an unclassified heartbeat.
  • Message passthrough. The message is written as given (newlines stripped/rejected so one call is one event line); mx-report never rewrites or summarizes it.
  • Same file, same grammar. The output line is byte-compatible with what a hand-written append produces today, so every downstream reader — mx-classify-lib.sh, mx-actor-state.sh, the watcher, the daemon — needs zero changes.
  • Home resolution as elsewhere: resolves the status path through the standard MX_HOME/MX_STATE_OVERRIDE chain, so tests can point it at a temp state dir.
  • Plan 04 seam: after a successful durable append, mx-report will attempt the optional watcher nudge (Plan 04). In this plan that hook is a no-op.

Path 2 — MCP report_status tool (harnesses with MCP support)

{
  "name": "report_status",
  "description": "Report a task status event to the broker. The only supported
                  way to report status; states outside the enum are rejected
                  by schema before execution.",
  "inputSchema": {
    "type": "object",
    "properties": {
      "state":   { "type": "string",
                   "enum": ["working", "paused", "blocked", "needs-decision",
                            "done", "failed", "resolved"] },
      "message": { "type": "string", "maxLength": 300 },
      "key":     { "type": "string", "pattern": "^[A-Za-z0-9._-]+$" }
    },
    "required": ["state", "message"],
    "additionalProperties": false
  }
}
  • Schema is the gate. The harness validates the call against the JSON schema before the tool ever executes — a malformed state never reaches our code at all. Stronger than the shell wrapper's own checking.
  • Implementation: a small stdio MCP server, bin/mx-report-mcp.mjs (node stays a kept runtime per UPDATE_PLAN §8.3, and the repo already ships .mjs command-policy scripts as precedent). Its tool handler execs bin/mx-report — one owner for the append, the enum constant, and (later) the Plan 04 nudge; the MCP layer adds only the schema gate and the session lifecycle.
  • Task identity: the server is launched per task session with the task id and home baked into its registration (env/args in the MCP config entry), so the tool schema needs no task_id parameter the model could get wrong.
  • Lifecycle: registered in the harness's own MCP config (e.g. .mcp.json for Claude Code, placed in the actor's worktree by the spawn path), so the server starts and stops with that harness session automatically. It is not part of mx-watch.sh or any always-on watcher process — entirely separate lifecycle, exactly as UPDATE_PLAN §3 requires.

Write scoping — mx-report refuses cross-task writes

Scope addition · 2026-07-27
Approved by the maintainer 2026-07-27. As written, this plan validates what gets written but not who writes it: any actor with shell access could run mx-report --id <someone-else> and poison the classifier's input for another task. Addition: mx-report resolves the calling session's own task id and refuses a mismatched --id — writes nothing, exits non-zero, and prints the mismatch to stderr (the same fail-loud pattern as an invalid state). The caller's id comes from the spawn path, never from trusting the argument. mx-brief.sh bakes the literal state/<id>.status path into the generated brief, and mx-spawn.sh already injects env into the actor's pane and records worktree= in state/<id>.meta. The spawn path therefore exports MX_TASK_ID into the actor session via that same pane-env mechanism; as a fallback/cross-check, mx-report resolves its working directory against the worktree= recorded in state/*.meta. If no binding can be established at all, it fails closed with a distinct error rather than writing unscoped. The MCP report_status tool gets the same check server-side: the server already knows the session's task binding (step 4 bakes MX_TASK_ID into its launch env) and refuses to serve without it — and since the tool schema has no task_id parameter, a cross-task write cannot even be expressed over MCP. This is soft enforcement — an actor with raw shell can still append to any file directly, exactly as the instructed-path-drift risk below records — but the plan's premise is that agents are instructed to report through the wrapper, so the wrapper must enforce every boundary it can see.

Per-harness wiring — .agents/skills/harness-adapters

The harness-adapters skill is already the one seam for per-harness quirks (spawn shapes, trust dialogs, skill invocation). It gains a "status reporting" section stating, per verified harness: MCP-capable → the spawn path writes/merges the report_status entry into that harness's MCP config and the brief names the tool; not MCP-capable → the brief instructs bin/mx-report directly. The generated brief always documents mx-report as the universal fallback, so a harness whose MCP session failed to start can still report validly.

Brief generator update — mx-brief.sh

Rule 4 of the delivery and scout scaffolds changes from the raw append to the validated path (keeping every existing behavioral instruction about sparse reporting, paused: vs blocked:, keyed decisions, and resolved-closure intact):

   (mx-report rejects anything else and prints the valid options — fix and
   retry). Never write to the status file by hand.
Invariant — must hold at review time
Both write paths append to state/<id>.status in the existing line grammar. mx-actor-state.sh and the reconciliation logic are byte-for-byte unchanged by this plan; the existing actor-state and classify test suites pass without modification. This change is additive to the event-log model, not a replacement.

Scope addition 2026-07-27 — task-binding cases: a server launched without MX_TASK_ID refuses tools/call (fail closed) without a write; a server bound to task a only ever appends to state/a.status, never another task's file.
  • Brief-content test (in tests/mx-brief.test.sh) — generated delivery and scout briefs instruct agents to use mx-report (and the report_status tool when available) and contain no echo "… " >> …status instruction.

Risks & open questions

Implemented deviation · 2026-07-28 — session-scoped MCP composition
The implementation does not edit or merge a project's committed MCP files in its task worktree. Verified local harness surfaces provide a safer session-scoped composition seam: Claude Code 2.1.220 receives a generated mode-0600 fragment at /tmp/mx-<id>/report-mcp.json through --mcp-config, while codex-cli 0.146.0-alpha.3.1 receives the equivalent mcp_servers.multplx_status table through per-run -c configuration. Both approaches compose with existing project configuration without dirtying or clobbering it and expire with the actor session. Pi remains on the universal mx-report fallback because no project-scoped Pi MCP registration contract was available to verify. Spawned sessions also receive MX_REPORT_STATE_OVERRIDE so a persistent daemon can keep its own operational MX_HOME while reporting to the parent task's status directory.
Decided · 2026-07-26 — enum is the full vocabulary
Maintainer decision: option (a) — the enum is extended to the full actor-writable classifier vocabulary, working|paused|blocked|needs-decision|done|failed|resolved, verified against bin/mx-classify-lib.sh (paused is the expected-idle pause verb; resolved closes an open keyed decision). Option (b) — keeping UPDATE_PLAN §3's five-state enum literally and leaving paused/resolved on the raw-append path — is rejected: it would force actors to hand-append exactly the lines we just told them never to hand-write. §3's five-state enum was simply incomplete. The broker-side maintainer-held transfer verb stays out of the enum; it is never actor-written.
Open question — MCP config placement and merging
Exact per-harness MCP config filename/location (Claude Code's .mcp.json in the worktree vs. a home-level config) and the merge policy when a project already commits its own MCP config are per-harness facts to be verified and recorded in harness-adapters during implementation, not assumed here.
Risk — instructed-path drift (low)
Agents can still bypass the wrapper with a raw append; the file stays writable by design (the whole model is append-only events plus reconciliation). Mitigation is instructional (brief text) plus Plan 05, which ranks schema-validated self-reports above heuristics — a hand-written malformed line simply keeps today's (unclassified) behavior, so the failure mode is never worse than the status quo.
Risk — MCP server availability (low)
If the harness fails to start the MCP server, the tool is absent but mx-report still works — the brief names it as the universal fallback. No wake path depends on the MCP server existing.
