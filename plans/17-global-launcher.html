Plan 17 · Multplx

Global Launcher and Activated Shell

Turn multplx into a command that works from any directory, activates one persistent multi-project control plane, preserves the user's tmux, Herdr, or cmux environment, and lets the user choose Claude, Codex, or Pi without copying state or installing a resident TUI.

Phase 11 · Global distribution Effort: Medium-High Risk: Medium Maintainer request · 2026-08-02 Decided: shell/Bash implementation

Overview

Multplx is currently a repository-based distribution whose root is simultaneously the harness discovery root and, by default, the operational home.

A user must clone the repository, change into its root, and launch one verified coding-agent harness there so that AGENTS.md, skills, project configuration, hooks, extensions, and scripts are discovered.

The product model is broader than that launch ritual.

One broker coordinates any number of registered projects, resolves a project independently for every request, and dispatches isolated work through a runtime backend and worker harness chosen independently of the broker's own terminal and harness.

Plan 17 makes that existing control plane globally launchable without changing its project, state, reporting, supervision, or delivery semantics.

Decided · shell activation, not a resident TUI

The implementation is a small shell/Bash launcher plus Bash and Zsh prompt adapters. The launcher prepares the environment and then replaces itself with the user's interactive shell. It does not enter raw mode, allocate a pseudo-terminal, render frames, poll state, or remain as a proxy between the user and Claude, Codex, or Pi. The subtle multplx prompt marker is the entire TUI presentation in v1.

Control-plane identity

MX_HOME identifies one persistent Multplx instance containing all project clones, registries, reports, artifacts, queues, and runtime state. It is not a project selector. The directory from which the user types multplx is preserved for shell convenience and is never inferred as a project or registered automatically.

Single-broker invariant

Exactly one broker may hold the session lock for an MX_HOME. The launcher may perform a read-only friendly preflight, but bin/mx-lock.sh and bin/mx-session-start.sh remain the only lock and startup authorities. A known live holder causes a new harness launch to refuse; a race still converges through the existing atomic lock claim, and the losing session remains unable to mutate the home.

Independent selection axes

CONTROL PLANEone persistent MX_HOME
BROKER SURFACEterminal, tmux, Herdr, or cmux
BROKER HARNESSClaude, Codex, or Pi
WORKER PROFILEharness, model, effort, backend
PROJECTresolved per request from the registry

The launcher owns only activation of the first axis and presentation of the shell.

It preserves ambient runtime signals for the second axis, lets the user select the third axis by typing a harness command, leaves the fourth axis to existing dispatch precedence, and leaves the fifth axis to normal broker intake.

  • No full-screen TUI, terminal compositor, pseudo-terminal wrapper, dashboard, or status monitor.
  • No multiple named homes or simultaneous brokers for one home.
  • No project selection from pwd, no automatic project import, and no single-project workspace mode.
  • No coupling between broker harness, worker harness, runtime backend, and project.
  • No new state, report, artifact, registry, status-event, or delivery format.
  • No global AGENTS.md or global broker hooks that affect ordinary coding-agent sessions.
  • No bypass of repository or hook trust prompts.
  • No Python, Rust, Go, Node package, or native TUI dependency on the activation hot path.
  • No Windows support in v1 because the current product supports macOS and Linux.

Target installation and path model

${XDG_CONFIG_HOME:-$HOME/.config}/multplx/
  root                 # one literal absolute path, never sourced as shell code
  home                 # one literal absolute path, never sourced as shell code

${XDG_BIN_HOME:-$HOME/.local/bin}/multplx
  # stable tiny bootstrap that reads root/home and execs bin/mx-launcher.sh

${XDG_DATA_HOME:-$HOME/.local/share}/multplx/
  runtime/             # default managed plain git clone for fresh installs
  home/                # default persistent MX_HOME for fresh installs
    config/
    data/
    projects/
    state/
  • Existing-checkout mode. The installer records the current checkout as both root and home by default, preserving its current data/, state/, config/, and projects/ in place.
  • Managed mode. A fresh install creates a hidden plain clone for tracked code and a separate persistent home for private operational material.
  • No implicit migration. Moving an existing home's private directories into the managed layout is a separate explicit operation with a dry run, collision checks, and rollback; v1 does not need that move to deliver the global command.
  • No shell-sourced configuration. Path files contain one literal absolute path each. The launcher reads and validates bytes rather than evaluating user-controlled shell syntax.
  • Atomic installation. Bootstrap wrappers and path files are written to same-directory temporary files, permissioned, validated, and renamed into place.

Launcher architecture

user terminal
  └─ multplx bootstrap in ~/.local/bin
       └─ bin/mx-launcher.sh
            ├─ resolve + validate MX_ROOT / MX_HOME
            ├─ capture real claude / codex / pi paths before shim PATH
            ├─ preserve backend and terminal environment
            ├─ set MULTPLX_ACTIVE=1, MX_ROOT_OVERRIDE, MX_HOME
            └─ exec user's interactive shell with one shell adapter
                  ├─ source user's ordinary rc once
                  ├─ re-prepend Multplx harness shims
                  ├─ add static prompt/title marker
                  └─ wait for user command

user types codex|claude|pi
  └─ matching shim
       └─ bin/mx-launch-harness.sh <harness> [args...]
            ├─ validate selected verified harness + captured real binary
            ├─ read-only live-lock preflight
            ├─ preserve all arguments and environment
            ├─ cd -P "$MX_ROOT_OVERRIDE" in this child only
            └─ exec real harness

Why the shell stays outside the runtime root

The activation shell remains in the caller's directory so ordinary terminal use feels unchanged.

The harness shim is a child process, so its cd cannot persist into the parent shell.

Inside the harness, the working directory is the Multplx root, which preserves current instruction and hook discovery and keeps the existing persistent-cwd guard meaningful.

No prompt function executes Git, reads state/, invokes Node, or spawns any subprocess.

The marker is static for the lifetime of the activated shell, which keeps prompt redraw cost constant and prevents presentation from becoming another state consumer.

State, reporting, and artifact safety

  • One operational root. Every existing script receives the same explicit MX_HOME; individual test overrides remain unset unless the user deliberately supplied them.
  • No launcher state tree. The launcher stores installation paths under its config directory and never creates a shadow data/, state/, config/, or projects/.
  • Reports stay parent-bound. mx-spawn.sh continues injecting the parent home's report path and MX_REPORT_STATE_OVERRIDE into actors, so status MCP writes and mx-report append to the existing parent state.
  • Artifacts stay home-bound. Briefs, scout reports, vplan artifacts, gate records, workflow runs, delivery handoffs, journal events, and dashboard run records retain their existing producers and paths.
  • Runtime checkout stays clean. In managed mode, activation and prompt rendering write nothing into the tracked checkout; all private writes land below the configured home.
  • Exit is natural deactivation. Because activation uses a child shell, leaving it restores the caller's untouched environment without an unset script.

Single-broker behavior

  1. An activated shell is not itself a broker and does not acquire the session lock.
  2. Before starting a harness, the shim runs the existing read-only lock status path.
  3. A lock held by a different live harness produces one concise refusal naming the active PID and returns to the activated shell.
  4. A free or stale lock permits the harness to start; only session start decides whether stale state may be reclaimed.
  5. If two launches race after both observe a free lock, existing atomic lock acquisition decides the winner before mutation.
  6. The losing harness receives the existing read-only startup result and must exit rather than operating as a second broker.

The launcher does not invent a second reservation file unless a reproduced race demonstrates that starting the losing read-only harness is materially harmful.

  1. Define the launcher and installation contracts new - add exact path, command, validation, exit-code, nested-activation, and installation behavior to the headers and help of the new launcher scripts before implementing presentation.
  2. Build the stable global bootstrap new - create an installer that writes literal root/home path files and an atomic multplx bootstrap into the selected bin directory, supports existing-checkout and managed-clone modes, refuses collisions, and leaves private data untouched on reinstall.

  5. Add the three harness shims new - route Claude, Codex, and Pi through one launch owner that preserves exact arguments and ambient backend variables, checks a known live lock, changes only the child cwd, and executes the previously resolved real binary without recursion.
  6. Compose existing operator commands reuse - make multplx doctor and multplx update delegate to their existing script owners with the configured root/home rather than reimplementing probes or update logic.
  7. Update public setup and configuration guidance mod - change README and Getting Started to lead with installation plus multplx, document existing-checkout adoption, define the static prompt boundary, and keep manual clone-and-launch as a supported development fallback.

Testing plan

A. Static and installation tests

  • Run bash -n over every new shell script and existing repository formatting checks.
  • Install into isolated paths containing spaces, Unicode, and shell metacharacters; verify literal path files are read as data and never executed.
  • Verify existing-checkout mode records the selected root/home without moving, rewriting, or hashing private contents.
  • Verify managed mode creates a plain git clone, a separate home, required private directories, and a bootstrap on PATH.
  • Repeat installation and prove idempotence; a compatible installation converges, while unrelated existing files or symlinks refuse without overwrite.
  • Interrupt installation before each atomic rename and prove the previous working installation remains usable.
  • Verify reinstall and uninstall distinguish the launcher/runtime from private operational data; private data is preserved unless an explicit destructive option names it.

B. Activation and environment tests

  • Launch from the runtime root, home root, a registered project, an unrelated git repository, a directory with spaces, and /tmp; every case resolves the same configured root/home.
  • Verify the activated shell retains the exact caller cwd before and after a harness stub runs.
  • Verify MX_ROOT_OVERRIDE, MX_HOME, MULTPLX_ACTIVE, shim PATH, and captured real harness paths are correct and contain no recursive shim resolution.
  • Verify unrelated environment variables are preserved byte-for-byte, including locale, proxy, terminal, authentication, and user shell variables.
  • Verify TMUX, TMUX_PANE, HERDR_ENV, Herdr identifiers, and cmux identifiers survive unchanged.
  • Verify --backend auto leaves normal detection untouched and explicit supported values set only the session-scoped override; invalid values fail before shell launch.
  • Verify nested activation does not duplicate PATH entries, prompt markers, terminal-title hooks, or environment layers.
  • Exit the child shell and prove the parent cwd, PATH, prompt, variables, and aliases are unchanged.

C. Prompt and TUI-presentation tests

  • Source controlled Bash and Zsh fixtures with custom prompts, themes, options, aliases, completion, and PATH mutations; activation must preserve each fixture and append exactly one marker.
  • Assert Bash renders one readable left-prompt marker and Zsh renders one right-prompt marker at 40, 80, 120, and 200 columns without corrupting prompt-width accounting.
  • Assert color is disabled for NO_COLOR, TERM=dumb, and non-interactive stdout, while the plain marker remains understandable.
  • Assert the terminal-title escape is emitted only for supported interactive terminals and contains no cwd, project, token, or private path.
  • Run an automated pseudo-terminal fixture for Bash and Zsh that enters the activated shell, executes a command, launches a fake harness, returns to the prompt, and exits cleanly.
  • Have the fake harness emit alternate-screen enter/exit sequences, bracketed-paste toggles, colors, carriage returns, and Unicode; captured bytes must pass through unchanged because no TUI proxy owns the stream.
  • Send Ctrl-C, Ctrl-Z/continue, EOF, and terminal-resize events to the foreground fake harness and prove normal shell/job-control behavior and prompt recovery.
  • Crash and kill the fake harness at representative points; the activated shell must remain usable, and terminal raw/alternate modes must not be left behind by Multplx.
  • Verify the prompt hook performs no filesystem read, subprocess spawn, Git operation, state read, or network call per prompt.

E. Single-broker and lock tests

  • Free lock permits launch and session start records the launched harness PID, not the shim or activated shell PID.
  • A live lock held by another verified harness causes the shim to refuse before executing the real harness.
  • A stale numeric lock, malformed lock, non-regular lock, unreadable state directory, and PID-reuse mismatch retain the existing lock owner's conservative behavior.
  • Two simultaneous harness launches against one free home produce exactly one mutable owner; the loser cannot run bootstrap sweeps, drain wakes, arm supervision, spawn work, or write state.
  • Two activated shells with no launched harness are harmless and acquire no lock.
  • After the broker exits, the next launch can reclaim through normal session start and reconcile all existing work.

F. Multi-project, backend, and worker-dispatch tests

  • Create a home with at least three registry entries using different delivery and autonomy postures; activation from a fourth unrelated repository must not alter or reorder the registry.
  • Dispatch concurrent fake tasks to two different projects and prove every project path resolves below the configured home's projects/, never below caller cwd or runtime root.
  • Run a Pi broker fixture that explicitly dispatches Codex and Claude worker fixtures; task metadata must record each selected worker harness independently.
  • Exercise explicit per-task backend, session MX_BACKEND, local config, tmux detection, Herdr detection, cmux detection, and tmux fallback in precedence order.
  • Prove changing the broker harness does not change an explicit worker profile and changing the runtime backend does not change project or worker-harness selection.
  • Run existing batch-spawn, daemon, headroom, project-mode, and backend suites unchanged.

G. State, report, and artifact integrity tests

  • Snapshot the managed runtime and configured home before activation; activation plus prompt rendering must leave both byte-identical except for explicitly documented shell history behavior outside those roots.
  • Run session start and verify lock, watcher, wake, digest, and bootstrap records appear only under the configured home.
  • Spawn fake actors and write schema-valid status through both mx-report and the report MCP adapter; every event must reach the parent home's state directory.
  • Create a brief, scout report, vplan artifact, gate record, workflow run, journal event, delivery handoff, and viz run record through their canonical producers; every path must match the existing home contract.
  • Set a runtime root and home with different physical devices or symlinked parents; canonicalization must keep code and operational writes correctly separated.
  • Search the runtime checkout after the matrix and fail on unexpected untracked or modified files.

H. Failure and security tests

  • Missing root, missing home, missing AGENTS.md, linked task worktree root, dirty managed runtime, unsupported shell, missing harness, and malformed config each produce one actionable error without starting a broker.
  • Path files containing extra lines, NULs, newlines, command substitutions, or relative paths are rejected as data-validation failures and never evaluated.
  • A malicious user rc cannot replace the captured real harness path after activation; the shim invokes only the validated absolute binary captured before PATH shadowing.
  • Harness arguments containing spaces, quotes, glob characters, newlines, and leading dashes arrive byte-for-byte at the fake binary without eval.
  • Trust prompts remain visible and updates that change hooks require the harness's normal re-review.
  • No launcher, installer, or prompt path prints environment secrets, tokens, private registry contents, or absolute project paths in banners or terminal titles.

I. Performance acceptance

  • Benchmark the same interactive Bash and Zsh startup with and without Multplx across at least 50 warm runs and five cold runs on the maintainer's machine.
  • The median incremental activation overhead target is at most 30 ms and the warm p95 target is at most 75 ms, excluding the user's own shell rc time that both sides share.
  • The median fake-harness shim overhead target is at most 15 ms and the warm p95 target is at most 30 ms.
  • After activation settles, no Multplx launcher or UI process remains beyond the interactive shell itself.
  • An idle activated shell consumes no measurable Multplx CPU, performs no periodic reads or writes, and opens no sockets.
  • Prompt redraw adds no subprocess and no state-dependent work; repeated prompt rendering is measured separately from shell startup.
  • Performance evidence records OS, shell versions, filesystem, command, sample count, median, p95, maximum, and raw machine-readable samples.
  • If budgets fail, profile path canonicalization, shell rc composition, and shim dispatch before considering a compiled rewrite; no test or safety check is removed to hit a number.

J. Existing regressions that must remain green

  • Session-start nudge and digest suites for all three harness transports.
  • Session lock, watcher continuity, turn-end guard, arm guard, cd guard, and subagent guard suites.
  • Spawn, batch spawn, report status, daemon lifecycle, backend dispatch, headroom, and project-mode suites.
  • Doctor, system snapshot/view, catchup, vplan, viz, workflow, journal, gate, delivery, and teardown suites.
  • bin/mx-doc-audience-check.sh, git diff --check, local HTML links, and full accelerated regression parity.

Risks and safeguards

Risk - shell startup files are arbitrary programs

User Bash and Zsh configuration can change PATH, prompts, aliases, options, and process behavior. The adapter sources the user's normal rc once, applies a minimal activation afterward, captures real harness binaries before shadowing, and tests hostile but valid rc fixtures. It never claims to sandbox the user's own shell configuration.

Risk - a prompt label grows into a status engine

The marker remains static and reads no state. Live actors, queues, decisions, and health already belong to mx-viz, mx-doctor, snapshots, and normal broker reporting. Adding dynamic prompt state would create polling cost and another interpretation surface.

Risk - hidden full-access runtime

A managed Multplx checkout contains trusted project hooks and Codex host-access configuration. Installation validates ownership and permissions, never bypasses hook trust, and makes the resolved root visible through multplx paths before the user approves trust.

Risk - path indirection obscures debugging

Every error names the resolved root and home safely, multplx paths is read-only, doctor runs against the same explicit environment, and all script owners continue deriving paths through their current precedence rather than a launcher-only global.

Deferred - true fixed terminal status bar

A status bar that remains visible while a coding agent owns the screen would require a PTY proxy and terminal compositor. That is intentionally outside v1 because it adds signal, resize, raw-mode, alternate-screen, and nested-TUI failure modes for no control-plane benefit. Revisit only after the static activated-shell marker is proven insufficient.

Definition of done

  • After one explicit installation, multplx works from any directory on supported macOS and Linux shells.
  • Bare multplx opens an activated child shell that preserves caller cwd and visibly identifies the environment without a resident TUI process.
  • The user can launch Claude, Codex, or Pi, and each harness loads the same Multplx instruction, skill, hook, extension, and script surfaces as a manual repository-root launch.
  • The surrounding tmux, Herdr, or cmux environment and normal backend precedence remain intact.
  • One MX_HOME continues to contain all registered projects, state, reports, artifacts, and configuration, with no shadow copy created by the launcher.
  • Concurrent launch tests prove exactly one mutable broker lock owner per home.
  • Multi-project tests prove caller cwd, broker harness, worker harness, backend, and project remain independent axes.
  • Bash and Zsh presentation tests cover prompt composition, narrow widths, colors, terminal titles, alternate-screen bytes, job control, signals, resize, crashes, nested activation, and clean exit.
  • Performance targets pass with no prompt subprocess, no polling, no socket, no periodic file access, and no resident launcher process.
  • Existing functional, safety, documentation, and accelerated full-regression suites remain green.
  • README and Getting Started lead with the global command while retaining a documented manual development launch fallback.
