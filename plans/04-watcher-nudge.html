Plan 04 / 10

Low-Latency Nudge — Wake the Watcher Without a Daemon

After its durable status append, mx-report sends a pure fast-path nudge — a liveness-verified SIGUSR1 to the watcher's advertised PID — so the watcher wakes immediately instead of at its next poll. If nobody is listening it is a silent no-op and the normal MX_POLL polling (default 15s) picks the event up unchanged. No HTTP daemon, no new persistent process, no new restart-proofing burden.

Phase 3 Effort: Low Risk: Low UPDATE_PLAN §4

Overview

Every status event today waits for the watcher's poll cycle: bin/fm-watch.sh sleeps FM_POLL (default 15s, becoming MX_POLL) between scans, so a status append lands on average ~7.5 seconds before anyone reads it. UPDATE_PLAN §4 records the rejected idea for closing that gap: a standalone HTTP status-ingest listener. It would cut the latency, but it reintroduces a long-running stateful process — and that cuts directly against the design virtue this codebase is built around: everything is reconstructable from disk; kill any process and the next one reconciles with zero daemon state to restore.

The better fit, chosen by UPDATE_PLAN §4: have mx-report (the validated status writer from Plan 03) optionally send a signal (or write to a named pipe) to the watcher's PID as a pure fast-path nudge. The durable write to state/<id>.status happens every time regardless; the nudge just wakes the watcher immediately instead of it waiting for its next poll. If nobody's listening, it's a silent no-op and the event falls back to normal polling.

This works with the grain of the existing architecture rather than around it: the watcher already advertises its identity durably on disk (the singleton lock at state/.watch.lock/ stores the holder's pid and a PID-reuse-proof pid-identity record, and state/.last-watcher-beat is touched every cycle as a liveness beacon). The nudge only has to read what is already there, verify liveness carefully, and signal. The one real design constraint is race safety — a stale PID must never be signaled — and the existing identity machinery in bin/fm-wake-lib.sh (fm_pid_alive, fm_pid_identity) already solves exactly that problem for the lock; the nudge reuses it verbatim.

Goals & Non-goals

GoalsNon-goals
  • Sub-poll wake latency for status events reported through mx-report (both the shell path and the MCP report_status path, which execs the same wrapper).
  • Durable-first: the state/<id>.status append always happens, and always before any nudge attempt; nudge failure never changes mx-report's exit status.
  • Silent no-op fallback: no watcher, dead watcher, stale lock, unsupported platform — all degrade to today's MX_POLL polling with zero errors surfaced to the actor.
  • Race safety: never signal a PID that cannot be proven to be the live watcher (liveness + stored-identity match immediately before kill).
  • Keep the restart-reconstructable-from-disk property intact: the nudge carries no payload and creates no state the watcher must recover.
  • No HTTP daemon or socket listener of any kind (explicitly rejected in UPDATE_PLAN §4).
  • No payload in the nudge: the wake reason still comes from the watcher's own scan of state/. The signal means only "scan now".
  • No change to what the watcher surfaces vs. absorbs — classification is untouched (that's Plan 05).
  • No nudge for hand-written appends: only the instructed mx-report path gets the fast path; raw appends keep pure polling.
  • No nudging of the away-mode daemon (fm-supervise-daemon.sh's successor) in this plan — polling cadence there is unchanged.

Target design in Multplx

Why not the HTTP daemon (decision record)

Rejected — standalone HTTP status-ingest listener
It would reduce latency (avg. ~7.5s against a 15s poll interval) but reintroduces a long-running stateful process, which cuts against the system's actual design virtue: everything is reconstructable from disk — kill any process and the next one reconciles with zero daemon state to restore. A listener also adds a port, an auth story, and a second wake path that could disagree with the durable one. Rejected per UPDATE_PLAN §4.

Sender side — mx_nudge_watcher in mx-report

  • Runs only after a successful durable append; wrapped so any failure is swallowed (|| true) and never alters exit status or prints to the actor unless MX_NUDGE_DEBUG=1.
  • PID discovery: read state/.watch.lock/pid under the same home resolution the append used. Missing lock dir or unreadable pid → no-op.
  • Liveness + identity verification (the stale-PID rule): a stale PID must never be signaled. Verify, immediately before kill: (1) fm_pid_alive "$pid" — the process exists; (2) fm_pid_identity "$pid" output equals the stored state/.watch.lock/pid-identity — the process is the same process that claimed the lock, not a PID-reuse impostor. Either check failing, or the identity file missing, → no-op. This matters doubly for signals: SIGUSR1's default disposition terminates a process that hasn't trapped it, so signaling a reused PID could kill an innocent process — the identity match is the guard.
  • Signal: kill -USR1 "$pid" 2>/dev/null || true. No payload, no retry, no waiting for acknowledgment — the durable file is the message; the signal is only "look now".
  • Opt-out: MX_NUDGE=0 disables the sender entirely (useful in tests that want deterministic pure-poll behavior).

Receiver side — interruptible wait in mx-watch.sh

The one subtlety: bash runs a trap handler only after the current foreground command completes, so a bare sleep "$POLL" would still block the full interval even with a USR1 trap installed. The fix is the standard background-sleep pattern — the wait builtin is interruptible by a trapped signal:

# at watcher startup (after the lock is claimed):
trap ':' USR1          # nudge = "wake from wait"; handler body deliberately empty

# in event_wait_or_sleep, every `sleep "$POLL"` becomes:
mx_interruptible_sleep() {  # <secs>
  sleep "$1" &
  local sp=$!
  wait "$sp"           # returns immediately (>128) when USR1 arrives
  kill "$sp" 2>/dev/null || true   # reap the sleeper on early wake
}
  • An early return from wait simply falls through to the next loop iteration — the same scan that a natural poll expiry runs. No new code path decides what to do; the nudge only decides when.
  • The trap is installed only in the main watcher process, after the singleton lock is claimed and pid/pid-identity are written — so the advertised PID and the trap-holding PID are the same process by construction.
  • The SIGNAL_GRACE linger (30s coalescing window after a signal) and the herdr event-wait branch are untouched; on a push-capable herdr session the native event path is already sub-second and the nudge is simply redundant there.
  • Coalescing is free: multiple nudges during one scan collapse into at most one extra wakeup, and a nudge that lands mid-scan is absorbed by the next wait returning instantly once — the scan is idempotent over state/.

Signal vs. named pipe (design decision)

Portability notes (macOS / Linux)

  • kill -0, kill -USR1, trap … USR1, and background-sleep+wait are POSIX and work identically on macOS bash 3.2 and Linux bash 4/5 — matching the repo's existing bash-3.2 floor (see the portable folds in fm-classify-lib.sh).
  • PID-identity portability is already solved by fm_pid_identity: Linux uses /proc starttime + cmdline hex (immune to wall-clock steps); macOS uses locale-pinned ps lstart+command. The nudge inherits both branches for free by sourcing mx-wake-lib.sh.
  • kill across users fails with EPERM — harmlessly caught by the || true; the nudge is only expected to work within one maintainer's own session, which is the only supported topology anyway.
Invariant
The durable append happens every time, before any nudge, and the poll loop remains the permanent fail-closed backstop at MX_POLL (default 15s). The nudge can only ever shorten latency; a lost, blocked, or skipped signal changes nothing about which events are surfaced — only when.

  • docs/architecture.md and docs/watcher-continuity.md: document sender identity checks, USR1 interruption, polling fallback, and the no-new-daemon decision.

(b) Existing tests needing changes

  • None expected. If any watch-triage case turns out to assert exact sleep timing (none found in the header contract), it gets MX_NUDGE=0 plus the existing tight-poll knobs rather than a semantic change.

(c) New tests to write — tests/mx-nudge.test.sh

  • Nudge wakes a running watcher early: start a real watcher with a deliberately long MX_POLL (e.g. 30s) and no pending work; from a second process run mx-report --state blocked …; assert the actionable wake is enqueued and the watcher exits in well under the poll interval (measure wall-clock; assert < MX_POLL/2, generous against CI jitter).
  • No listener → silent no-op: no watcher running (no state/.watch.lock/): mx-report exits 0, stderr empty, status line present; then with only a stale lock dir left behind by a killed watcher: same result.
  • Stale PID is never signaled: construct a lock dir whose pid names (1) a dead PID, and (2) a live decoy process whose identity does not match the stored pid-identity — the decoy traps USR1 and records delivery to a file; run mx-report; assert the decoy never received the signal, mx-report exited 0, and the append happened. This is the direct test of the "verify liveness before kill" rule.
  • Durable write happens in all cases: for each scenario above (live watcher, no listener, stale lock, MX_NUDGE=0, identity mismatch), assert the status line landed byte-identically — the nudge outcome never affects the write.
  • Opt-out: with MX_NUDGE=0 and a live watcher, assert no early wake (watcher still blocking after a short delay) and the event is picked up by the natural poll (run with a short MX_POLL for this case).

Risks & open questions

Risk — TOCTOU between identity check and kill (accepted, negligible)
A theoretical window exists where the watcher dies and the OS reuses its PID between the identity verification and the kill. The identity check runs immediately before the signal, the OS does not reuse PIDs at microsecond scale, and the same window exists (and is accepted) in the lock-steal logic in fm-wake-lib.sh today. Consequence is bounded to one spurious USR1 to a process that would have to have spawned in that instant.
Open question — should the away-mode daemon also listen?
While state/.afk exists the daemon owns triage and the watcher runs one-shot. UPDATE_PLAN §4 names only the watcher. Extending the nudge to the daemon (its own PID advertisement + trap) is mechanical but out of scope here; decide when the daemon is ported.
Open question — FIFO fallback trigger
If a supported platform ever proves signal delivery unreliable (e.g. exotic sandboxing that blocks kill between sibling processes), the named-pipe design (state/.watch-nudge.fifo, non-blocking write, reader integrated into the interruptible wait) is the recorded fallback. No evidence today warrants building it; revisit only on a concrete failure.
Risk — trap interaction with the herdr event wait (verify in step 4)
On a push-capable herdr session the terminal wait is a reader subprocess, not sleep. A USR1 to the main shell during that wait is deferred until the foreground reader returns (bounded at ~MX_POLL), which merely equals today's latency for that branch — and herdr's native events already beat the nudge there. Confirm with the existing eventwait smoke test (tests/fm-backend-herdr-eventwait-smoke.test.sh) that nothing regresses.
