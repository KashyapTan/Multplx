agent distro · bash orchestration layer

firstmate

Talk to one agent. Ship with a crew. firstmate turns a single terminal coding agent into a fleet supervisor. You chat only with the "first mate"; it spawns autonomous coding agents ("crewmates"), each in its own git worktree and terminal, watches them with a zero-token bash loop, and hands you finished PRs, approved merges, or investigation reports.

no app to install — the repo IS the distro bash + git + gh tmux / herdr / zellij / orca / cmux claude · codex · grok · pi · opencode

01 The core idea

firstmate is not a model, harness, CLI, or MCP server. It is an agent distro: a directory of instructions (AGENTS.md), skills, and helper scripts (bin/) that any terminal agent reads to become a fleet supervisor.

The captain

You. You talk to exactly one agent, in plain language: "fix the flaky test and add dark mode." You make decisions and approve merges.

The first mate

The agent you chat with. It never edits your projects itself. It routes work, spawns crewmates, supervises, and reports outcomes.

The crew

Autonomous agents it spawns. Each gets a clean worktree + visible terminal and does the actual coding, then ships a PR or leaves a report.

Prime directive: the first mate is read-only over your projects. Only crewmates change code, and only behind the configured merge authority. State lives on disk + the session backend, so any session can be killed and the next one reconciles and carries on.

Between the first mate and the crew sits a zero-token bash watcher — it sleeps on the fleet and only wakes the first mate's LLM when something is genuinely actionable. This is what makes running many agents cheap. Detailed in §05.

03 The four layers

The system stacks cleanly. Each layer only knows about the one below it.

LayerWhat it isKey pieces
1 · Instructions The always-loaded operating contract the agent reads to become the first mate. Prime directives, task lifecycle, supervision rules, escalation etiquette. AGENTS.md (CLAUDE.md is a symlink), .agents/skills/
2 · Toolbelt ~90 bash scripts the instructions call. Spawn, supervise, steer, classify wakes, tear down. The agent orchestrates by running these — it doesn't reimplement them. bin/fm-*.sh
3 · Backend abstraction A session-provider seam. Every "create a terminal / read it / send keys / probe if busy" call goes through one dispatcher to a pluggable adapter. bin/fm-backend.sh → bin/backends/*.sh
4 · State on disk All truth. Per-home directories hold the backlog, task metadata, status logs, and coordination locks. Nothing important lives only in conversation. data/ state/ config/ projects/

04 A task's lifecycle

Every unit of work — a ship (changes code) or a scout (produces a report) — moves through the same arc. Each stage is owned by one script.

brief→ spawn→ supervise→ steer→ validate→ land / report→ teardown

brief · fm-brief.sh

Scaffolds data/<id>/brief.md — the contract handed to the crewmate. Defines the status vocabulary (paused: / blocked: / done:) the watcher later reads, and the delivery-mode "definition of done."

spawn · fm-spawn.sh

Creates a backend terminal + a clean worktree, writes state/<id>.meta (the record every other script keys off). Refuses to launch unless the worktree is genuinely isolated from your checkout.

supervise · fm-watch.sh

The zero-token loop. Classifies each wake in bash; surfaces to the LLM only when actionable. (§05)

steer · fm-send.sh

The actuator. Sends one line of text to a crewmate and confirms the backend accepted it — fails loudly if the keystroke was swallowed.

validate

Delivery mode owns rigor: no-mistakes runs a full gated pipeline → PR; direct-PR just opens a PR; local-only stops at a clean branch for an approved fast-forward merge.

teardown · fm-teardown.sh

Closes the lifecycle: returns the worktree, kills the terminal, clears state — but refuses if work hasn't landed. Uncommitted or unmerged work is never discarded without explicit authority.

Two task shapes

SHIP (default)

Produces a project change through the selected delivery mode. Ends in a PR, an approved local merge, then cleanup.

SCOUT

Produces knowledge at data/<id>/report.md — investigation, diagnosis, planning, audit. Never pushes. A report can recommend a change but does not authorize one; it can later be "promoted" into a ship.

05 The supervision engine — the clever part

Running many agents naively means burning tokens polling each one. firstmate's answer: a bash watcher that does all the triage for free, and only spends an LLM turn on real events.

Normal mode · fm-watch.sh

An always-on bash loop sleeps on the fleet. For each "wake," it classifies in bash: is this a real signal, a stale/stuck worker, an authenticated check result (PR merged?), or just a heartbeat? Benign wakes are absorbed silently — no LLM turn. Only actionable wakes go to a durable state/.wake-queue and wake the first mate.

Away mode · fm-supervise-daemon.sh

When you type /afk, a daemon wraps the watcher and handles even more in bash — self-resolving routine notifications and batching only captain-relevant events into single-line digests injected into your pane. Gated by the state/.afk flag; any normal message you send ends it.

Why it's "provably working": the watcher never trusts a stale status line. A crewmate's state/<id>.status is an append-only event log, not current truth. To decide whether a quiet worker is fine or wedged, it calls fm-crew-state.sh — the "truth oracle" — which reconciles the log against the actual running validation step and terminal busy-signature, matched by branch and code identity.

Shared brain, two engines

Both the always-on watcher and the away-mode daemon source the same classifier (fm-classify-lib.sh) so triage policy can never drift between them. It defines what counts as "captain-relevant" (done:, needs-decision:, blocked:, failed:…) versus an absorbable heartbeat.

Restart-proof by construction

  • Durable queue: actionable wakes are written to state/.wake-queue before detector state advances, so a missed process exit is recovered by draining the queue.
  • Singleton lock: a race-proof lock guarantees exactly one watcher per home; siblings self-evict.
  • Turn-end backstop: on verified harnesses, a Stop-hook blocks a "blind" turn end while work is in flight and no live watcher exists.
  • Liveness beacon: state/.last-watcher-beat is touched every poll; guard scripts alarm if it goes stale.

06 Isolation — worktrees, not branches in your checkout

Parallel work on one repo never collides because each crewmate gets its own git worktree. The first mate literally cannot spawn a task unless the worktree is proven distinct from your primary checkout.

treehouse

Pools clean, disposable git worktrees for tmux / herdr / zellij / cmux tasks. Returned and recycled at teardown.

orca-managed

When backend=orca, Orca owns both the worktree and the terminal, and removes worktrees via orca worktree rm after teardown checks pass.

tangle guard

Because firstmate can dispatch crewmates to work on itself, a dedicated check flags the one dangerous state: a named non-default branch checked out in the primary. It refuses to proceed and prints the repair.

07 Runtime backends

The "where does a crewmate's terminal live" layer is pluggable. One dispatcher (fm-backend.sh) resolves selection and routes every terminal operation to an adapter. Selection order: --backend flag → FM_BACKEND → config/backend → runtime auto-detect → default tmux.

BackendStatusWorktree providerContainer shape
tmuxReference / default ✓treehouseone window per task
herdrExperimental — auto-detect via HERDR_ENVtreehouseone workspace per home, one tab per task; native busy/blocked events
zellijExperimental — explicit onlytreehouseone shared session, one tab per task
orcaExperimental — explicit onlyorca (self)owns both worktree + terminal lifecycle
cmuxExperimental — macOS, GUI-firsttreehouseone workspace per task

Most backends are session providers only — tmux/zellij/orca/cmux have no native "is it busy?" primitive, so the watcher's poll over pull primitives (capture text, list live windows, regex the pane tail) is the event source. Herdr is the exception: it exposes native working/idle/done/blocked state, so the watcher can wait on a real event instead of polling.

08 State model — everything on disk

FM_HOME selects one first mate instance's private world. Scripts always run from the tracked bin/, but resolve data/ state/ config/ projects/ under that home. This is also how a secondmate (a persistent second mate with its own isolated home) works.

data/ — durable knowledge

backlog.md (the queue), captain.md (your prefs), learnings.md (fleet gotchas), secondmates.md (routes), projects.md (registry), and per-task <id>/brief.md + scout <id>/report.md.

state/ — volatile runtime

<id>.meta (authoritative task record), <id>.status (append-only wake-event log), .wake-queue, watcher locks & beacons, .afk, and X-mode inboxes.

config/ — local choices

backend, crew-harness, secondmate-harness, crew-dispatch.json (natural-language routing rules), plus calm / wedge-alarm / x-mode knobs. All gitignored, per-home.

projects/ — read-only clones

The repos firstmate works on. Read freely; mutated only through the guarded init / sync / merge exceptions. Crewmates change code in worktrees, never here.

The backlog (.tasks.toml) is a markdown-file backend: live queue in data/backlog.md, completed items archived to data/done-archive.md keeping the last 10 inline. Routine edits go through the tasks-axi CLI (or hand-editing if config/backlog-backend=manual).
The golden rule of state: a .status line is a wake event, never current truth. Anytime the live state matters, the code re-derives it with fm-crew-state.sh. This single discipline is what makes restarts a non-event.

09 Skills & advanced capabilities

Beyond the always-loaded AGENTS.md, behavior is packaged as skills loaded on demand at precise trigger points — keeping the base context lean.

Two-tier skill layout

.agents/skills/

Agent-loaded skills, meaningful only inside a live firstmate home (flagged metadata.internal: true so installers ignore them). Some are user-invocable (/afk, /ahoy, /bearings, /stow, /updatefirstmate); most are agent-only playbooks loaded at their trigger (harness-adapters, stuck-crewmate-recovery, secondmate-provisioning, diagnostic-reasoning, ask-user-authority…).

skills/

Public, installer-facing skills that stand alone in any project with no dependency on firstmate. Today: skills/stow, a generic session-knowledge-sweep skill.

Advanced capabilities (all optional)

  • Secondmates: persistent second mates running from their own isolated FM_HOME, with their own state, backlog, and projects. The primary launches and syncs them; they're idle by default and act only on routed work.
  • Dispatch profiles: natural-language rules in config/crew-dispatch.json let the first mate choose which harness / model / effort handles each task, judged against live quota headroom.
  • Project modes & +yolo: per-project delivery posture (no-mistakes / direct-PR / local-only) plus an optional autonomy flag that lets the first mate clear routine gates within your original request.
  • X mode: opt-in with one local token so the same fleet can answer public @myfirstmate mentions through the identical lifecycle as chat requests.
  • Self-update: /updatefirstmate fast-forwards the running distro (and secondmates) from origin, then re-reads instructions — never touching your project clones.

10 Reading this for a port

If you're rebuilding this as Orca, here's the conceptual skeleton worth keeping — and the seams where your customizations will live.

Keep — the load-bearing ideas

① One liaison agent, read-only over projects. ② Zero-token bash triage that only wakes the LLM on real events. ③ Status-log-is-an-event-not-truth + a truth oracle. ④ Worktree isolation enforced at spawn. ⑤ All state on disk → restart-proof.

Seams — where to customize

The backend adapter interface (fm-backend.sh) is the cleanest plug-in point. The skills layer is where behavior is added without touching the core contract. The classifier (fm-classify-lib.sh) defines your escalation policy in one place.

The instruction contract (AGENTS.md) and the toolbelt (bin/) are deliberately separate: the agent reasons from the instructions and acts through the scripts. That split is what lets any harness (Claude, Codex, Grok…) drive the same fleet. Preserve it, and the rest is swappable.
